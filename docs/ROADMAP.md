# HUME — Roadmap

## Editor — new features

- [ ] Persistent sessions — save and restore open buffers, splits/tabs, and cursor positions across restarts. **Decided: the session file also records recorded macros** (the `q` register and friends), since they're otherwise unrecoverable after quit and nothing else in the roadmap covers that gap (see Open questions' macro-register item, which this supersedes for persistence purposes). Whether *other* registers (numbered, `c`, `k`) are part of the session file is still open — see Open questions.
- [ ] Persistent undo across restarts — undo history is in-memory only today (`user-manual/docs/files-and-buffers.md`'s "Persistence and safety"); lost on quit, no cross-restart undo. Needs an on-disk format for the undo tree and a load path tied to buffer open.
- [ ] Code folding — tree-sitter-powered collapse/expand.
- [ ] Resizable panes — grow or shrink the focused pane along a split, with a count. Every pane sharing a split axis is equal-sized today: `equalize` (`hume-engine/src/pipeline/layout.rs`) rewrites every split's ratio in the tree on each split and close, so a resized ratio has to survive an unrelated split or close elsewhere. Undecided: keys under the `Ctrl-p` prefix, an equalize command to undo a resize, and resizing by dragging a pane border with the mouse.
- [ ] Sticky scope headers — while the top of a pane is inside a class or function whose first line has scrolled out of view, pin that first line (the class, then the method) above the pane's text, so the body on screen keeps its context (`nvim-treesitter-context`). The enclosing nodes can come from the `class.around`/`function.around` captures `textobjects.scm` already defines for text objects (`hume-treesitter/src/textobjects.rs`). Undecided: the most header lines shown before the outer ones drop, whether the headers cover text lines or push them down, and what clicking or jumping to a header does.
- [ ] Debugger support (DAP) — breakpoints, stepping, call stack, variables and a debug REPL through the Debug Adapter Protocol. A protocol separate from LSP, built on the same split: Rust transport, Steel behavior (`docs/LSP.md`'s "Deferred / Future").
- [ ] Command and search history picker — fuzzy recall of earlier `:` commands and `/`/`?` searches into the prompt, in place of the Up/Down-only recall in `minibuf/history.rs`.
- [ ] `:e` binary / huge-file y/n confirm — binary-sniff + size threshold. The reusable confirm-overlay primitive this needs (`ConfirmLayer`, `hume-editor/src/editor/input_stack/confirm.rs`) already exists, built for the disk-change reload prompt. The confirm belongs to the interactive `:e` path: `open-buffer!` stays non-interactive, since a plugin opening a file has no one to answer a prompt.
- [ ] Advertise `completionItem.resolveSupport` (`additionalTextEdits`) — `hume-lsp/src/initialize.rs`'s `build_client_capabilities()` leaves `CompletionItemCapability::resolve_support` unset, so a conforming server must put `additionalTextEdits` on every completion candidate up front rather than deferring the ones you don't accept; some servers gate whole features (suspected: rust-analyzer's flyimport, offering symbols from modules not yet imported, with the `use` added on accept) behind the client advertising this, rather than just doing it eagerly — unverified against rust-analyzer's own source. Advertising it needs two other changes first: accept's resolve reply (`ResolveBase::request`) currently drops silently (`hume-editor/src/editor/lsp/drain.rs`'s `anchor_admits`) if the buffer changed at all since accept, mapped only through the accept edit's own `ChangeSet` — it would need mapping through every edit since, not just that one, or an accepted import can vanish with no message when a server defers it lazily. And `CompletionItem::is_noop_for` (`hume-editor/src/editor/completion/item.rs`) currently treats a no-`textEdit`/no-`additionalTextEdits` candidate matching the typed text as a dropped no-op, reasoning that an LSP item can't be a no-op because a server must front-load edits without this capability — once a server *can* defer them, a fully-typed import-only candidate would be silently hidden by that same check.
- [ ] Saved selections (Kakoune's marks) — save the current selections to a register, restore them later, or combine them with the current ones (append, union, intersection, and per-pair leftmost/rightmost/longest/shortest). Builds a set of non-adjacent selections from any motions, where `s` needs a regex that matches every target. Saved selections are carried through edits by `PositionStores` (`hume-editor/src/editor/position_stores.rs`), like every other stored position. Undecided: keys (`z` is the view prefix here, unlike Kakoune), whether marks use ordinary registers or a dedicated store, and how pair-wise combining behaves when the two sets differ in count. Helix's unmerged attempts (helix#3720, helix#13649) raise the same questions.
- [ ] Auto-generated command reference + in-editor `:help` — there is no `:help` command; `:tutor` is the only in-editor documentation.
- [ ] LSP semantic tokens — highlight identifiers by what the server says they are (local, parameter, type, mutable binding), over tree-sitter's syntax highlighting. Design notes in `docs/LSP.md`'s "Deferred / Future"; undecided: priority against tree-sitter highlights.
- [ ] Streaming load for huge files — chunked read replacing single blocking full-file read. Scripts never observe a partial load: `on-buffer-open` fires once the read completes, and `buffer-text`/`buffer-line-count` cannot reach the buffer before then.
- [ ] Wrap indicator — configurable char prepended to continuation display lines in soft-wrap mode.
- [ ] Completion menu shows each item's source — a column naming where a candidate came from (`lsp`, `buffer-words`, a plugin's source), configurable. A row carries only the label and, when the documentation box is off or has no room, the item's `detail` (`CompletionItem::menu_row`, `hume-editor/src/editor/completion/item.rs`). Undecided: an option to turn the column on and off, and a per-source display name (e.g. `[LSP]`) passed to `register-completion-source!` in place of the registered name.
- [ ] Notifications in the bottom drawer — a drawer client for notification history, alongside `:ls`.
- [ ] Styled spans in `show-popup!` — the popup takes one flat string today, so signature help marks the active parameter as `⟨…⟩` on a second line instead of highlighting it in place. Wants a `(hash 'start-char 'end-char 'scope)` span list over the popup text: offsets into the popup text, as `diff-words` gives offsets into the texts passed to it. Its input already arrives: HUME declares `labelOffsetSupport`, so a server sends each parameter's offsets into the signature label.
- [ ] **[breaking]** Styled spans in the drawer — `lsp-locations->places` shows an unopened target's column as the location's own wire unit rather than a measured grapheme column (see `docs/LSP.md`'s "User-facing column unit" decision row); once a drawer row can style part of itself, render that unmeasured column visually distinctly (e.g. italic) instead of identically to a measured one. Wants the same per-row span support as the `show-popup!` item above. Changes the drawer row / `lsp-locations->places` shape.
- [ ] Scope-aware local rename without a language server — `core:lsp` renames through `textDocument/rename`; this is the fallback for a buffer with no server offering rename, resolving a name's scope from the grammar's tree-sitter `locals.scm`.
- [ ] Steel-side picker row display formatter — `#:truncate 'head|'tail` only picks which end of an over-long row is clipped; see `docs/FUZZY-FINDERS.md`'s "Remaining work" for the general per-row formatter this doesn't cover.
- [x] **[breaking]** `:ls` in the bottom drawer — `Enter` on a row switches buffer, so it is a jump. `(buffers)` and `on-text-changed` see no `[buffers]` buffer. `:messages` stays a read-only buffer so it can be navigated, selected and copied.
- [x] Buffer-words completion source — shipped as `core:buffer-words`, a Steel source (not a native `Buffer`-target `SourceBody` variant — see `docs/COMPLETION-PICKER.md`), built on the plugin-facing `register-completion-source!`/`completion-emit!` API so that API has an in-tree caller; the native minibuffer sources already exercise the Rust-internal machinery.
- [x] `:earlier` / `:later` undo-tree time travel — count + relative-age specs over the redo path; cross-branch jumps and history browsing ship in `core:undotree`, and its side-panel host is `docs/UNDOTREE.md`'s Phase 2.
- [x] **[breaking]** Fully rebindable picker keys — a picker answers only the keys its keymap binds, `Enter` and `Esc` included, and the plugin that opens it passes that keymap; `core:stdlib`'s `stdlib/picker-keymap` is the one default set, reused whole or with keys overridden.

## Editor — fixes & optimizations

- [ ] Minimum severity for `:messages` — an option naming the lowest severity the message log keeps, e.g. `'warning` to drop every trace entry, alongside `lsp-diagnostics-min-severity`, which filters diagnostics only. Language-server output is most of the volume: `window/logMessage` info/log entries and every stderr line are logged at trace level (`hume-editor/src/editor/lsp/drain.rs`). Undecided: whether a warning dropped under an `'error` floor still counts in `MessageLog::totals`, which `message_logged_this_input` (`hume-editor/src/editor/input.rs`) compares across each input.
- [ ] `:messages` follows the log — the `[messages]` buffer is a copy of the log taken when `:messages` runs (`typed_messages`, `hume-editor/src/editor/commands/typed_misc.rs`), and `MessageLog::push` never updates it, so a message logged while it is open appears only after running `:messages` again. Undecided: whether the cursor follows new entries when it is on the last one, and whether entries logged while the buffer is visible count as seen.
- [ ] Non-`file:` LSP location URIs (jdtls's `jdt://`, deno's `deno:`) — `goto-location!` rejects them outright and `lsp-locations->places` skips them, and goto and references warn once how many were left out (`hume_lsp::uri::uri_to_path` only understands `file:`); a server sending one is conforming, HUME just has no reader for it yet. `goto-location!`'s error names the URI and says it is not a `file:` URI, but the destination is unreachable.
- [ ] Coalesce repeated scroll events — `run_loop` reads one terminal event and renders, with no batching anywhere on the input path (`viewport_debounce` debounces the `OnViewportChange` hook, not the frame). A held scroll key or a fast wheel delivers events far quicker than a keystroke, and each drives a full `prepare_frame` + render; under soft wrap that formats every visible line per event, since `content_display_lines` formats a line just to count its display lines. Draining consecutive same-direction scrolls and applying them as one motion cuts the *number* of frames rather than the cost of each. Only worth building if held-key scrolling actually measures slow — but if it does, this is the cheaper answer to the problem the line-store cross-frame item under Performance — deferred describes, and should be tried first.
- [ ] Lazy-load shell dialects — `runtime/scheme/shells.scm` is evaluated at every startup, before `init.scm`, though only `Tab` on the `|` prompt reads it. Load the dialects when that `Tab` first needs one instead. `init.scm` and plugins call `register-shell-dialect!` and reuse the shipped `shell/posix-parse`/`shell/posix-write` (and the `fish`, `pwsh` and `cmd` pairs), so those names must still resolve when `init.scm` runs.
- [ ] Byte-string parsing in settings — `"10MB"` / `"512KB"` strings; companion to the size-threshold setting.
- [ ] Native directory-walker fallback for the file picker — for bare directories without `fd`; build only if the fallback posture proves inadequate in practice (see `docs/FUZZY-FINDERS.md`).
- [ ] `:sort --lexicographic` override — for when numeric auto-detection guesses wrong (e.g. `1.10` vs `1.9`). Not worth shipping until it actually bites.
- [x] Crash-safety net — on panic, a signal exit (`SIGHUP`/`SIGTERM`/…) or a terminal hangup, every dirty buffer is written to `<file>.dump` (scratch buffers to the data dir's `dumps/`), and opening a file that has a dump offers restore/discard/keep. A panic on a non-main thread shows as an error in `:messages` and does not stop the editor; the forced exit after the 3 s signal grace window writes no dump.

## Performance — deferred

Structural work, an invalidation contract, or a wide signature change — none is a small edit. Nothing here is measured as dominant: the benchmark harness is itself the first item.

- [ ] Criterion benchmark harness over `Editor::render_to_buf` — the only harness is `hume-rope`'s cluster-query bench, so every rendering item below is reasoned from allocation and complexity counts rather than from a profile. Build this before betting on any of them.
- [ ] Frame-level damage tracking — every frame re-formats, re-styles and re-composes every visible display line; only the cell diff in `hume-grid` limits terminal writes. The largest single win and the largest correctness risk (several per-frame sync steps have side effects).
- [ ] Line-store entries surviving a frame — **superseded; kept for the analysis, not as work.** Read the last two paragraphs before picking this up. It is the format-stage third of damage tracking above and would unblock it, but a cheaper fix covers the only case where it could matter. `EngineView::begin_frame` rewinds every pane's `PaneLineStore` unconditionally, so the store shares work only *within* a frame (the scroll step and the render pass) plus with a between-frame command that ran since the last one; across frames its value is zero. A 3-display-line scroll in a 50-display-line viewport discards ~94% of still-valid work, and an ordinary keystroke discards all of it.

  That rewind is a correctness requirement, not hygiene. `update_inlay_hint_providers` and `update_eol_text_providers` (`decoration_providers.rs`) rebuild their per-pane mirrors every frame *filtered to the viewport that frame shows*, and neither bumps `DecorationStores::generation` — so a line scrolling into view gains inline inserts, changing its wrap display-line count, while `FormatKey` sits unmoved.

  The fix is to remove that dimension rather than key on it: make both mirrors unfiltered and generation-gated, exactly as `update_virtual_line_providers` already is via `Editor::virtual_lines_synced`. All three shape-bearing mirrors then become pure functions of `(bid, decorations.generation(bid))`, which `FormatKey::buffer_tag` already folds in, and `begin_frame` demotes from correctness to memory reclamation. Unfiltering is close to free — the LSP publisher sets hints per viewport range, so the store holds roughly a viewport's worth either way — but the change needs an entry-eviction policy designed from scratch, since nothing would rewind the store per frame any more.

  Rejected alternative: putting the mirrors' build window into `FormatKey`. It works, but any viewport move then rewinds the whole store, so scrolling — the case with the most to reuse — never benefits.

  Unmeasured, like everything in this section. The render loop is event-driven and blocks fully when idle (`wake_timeout()` is `None` with nothing scheduled), so frames happen per input rather than on a clock — which is what the budget argument below rests on. Build the harness at the top of this section before betting anything on the numbers here.

  The simplicity cost is concrete: `begin_frame` is the store's only bound today, so demoting it means designing an entry-eviction policy where none exists, and unfiltering the two mirrors widens them from viewport-scoped to whole-buffer — a new cache with a new invalidation contract, which is the category the two `fix(editor)` commits in the original refactor were both about.

  Why superseded rather than merely deferred. One number decides this — the worst-case frame (largest realistic terminal, soft wrap, decorations on) — and both outcomes route elsewhere. Comfortably under a per-keystroke budget: ship nothing, a frame costs a keystroke and the headroom is enormous. Marginal: the problem is not per-frame cost but *sustained* input, and the cheaper answer is the scroll-event coalescing item under *Editor — fixes & optimizations*. Note the budget differs between those two cases and 60fps is the wrong frame for the second: under a held key the constraint is the inter-event interval (tens of events/sec, so ~20ms), and exceeding it shows up as backlog — the view still scrolling after the key is released — not as a low frame rate. A frame-time benchmark cannot see that, which is exactly why the fix is to cut the number of frames rather than the cost of each. Scrolling needs no benchmark of its own: a scroll frame is an ordinary frame, since even `scroll_back_from` walking backward from a distant cursor is bounded by viewport height.
- [ ] Two `ChangeSet` copies left where one edit's inserted text has two live owners: `EditGroup::compose` clones each Insert-session edit into the group because `apply_grouped_from` also returns it (completion accept reads it), and cycling a paste clones the new paste into the propagation `compose` while the group keeps its own. One keystroke's payload in the first case, a repeat paste in the second. Sharing the inserted text (`Operation::Insert(Rc<str>)`) removes both, since `compose` moves ops out of both sides.
- [ ] Statusline recomputes per frame — the `FilePath` two-pass sizing re-renders any section containing it (the default left section), and `DiagnosticsElement` scans the whole diagnostics store for its counts. Both want caching against a generation, not a mechanical fix.

## Plugins

- [ ] `core:lsp-install` `cargo-git` install flavor — installs from a pinned git tag instead of crates.io semver; unblocks `nil`.
- [ ] **[breaking]** Per-buffer plugin exclusion — enable a plugin everywhere except for chosen languages or file patterns, e.g. `core:buffer-words` on for every buffer but `*.min.js`. `declare-plugin!`'s `#:languages` only picks what triggers loading; once active, a plugin acts on every buffer. Exclusion therefore has to be checked per buffer each time the plugin would act, not once at activation. Changes when every plugin's hooks, commands, and completion sources fire.
- [ ] Session-scoped hooks — `register-hook!` works only during init or plugin load, so a plugin with a transient UI session keeps its hook for the rest of the editor's life and filters inside the handler: `core:undotree`'s `on-undo-history-changed` and `core:lsp`'s locations `on-text-changed` both fire on every change and return early when no drawer is open. A pair that can be called from a command body would let a session listen only while it is open: a register call that returns a handle, and an unregister call that takes it, with the handle tied to the session's owner so plugin rollback still removes it. Cheap today (one Steel call per change that returns immediately); worth building when a third client appears or a profile shows the calls.
- [x] `:lsp-install` argument completion — a `#:target 'minibuf` source over the installable server names, declared via `define-typed-command!`'s `#:complete`.
- [ ] Per-language user scripts — a `languages/` directory next to the user's `init.scm`, one `<language>.scm` per language, run when a newly loaded buffer has its language set (Neovim's ftplugin). These files are code, evaluated as Steel, unlike the data-only `runtime/scheme/languages/<name>.scm` files, which are parsed and never run.
- [ ] Color highlighter plugin — inline-highlight hex color literals (`#abcdef`, `#0365AF01`) in a buffer, like `nvim-colorizer.lua`. Needs a new Steel builtin to set a decoration whose background/foreground is computed from arbitrary RGB(A), not one of the theme's fixed scopes.

## Open questions

- **[breaking]** Multiline quote text objects — currently line-bounded (parity scan gives wrong results across unmatched quotes on earlier lines); use tree-sitter to resolve when a grammar is loaded, fall back to line-bounded parity otherwise. `miq`/`maq` results change once a grammar is loaded.
- **[breaking]** `goto-matching-pair` tag matching (`#` on `<tag>`) is a lexical scan, while the tag objects and navigation (`m i x`/`m a x`, `g x`/`g X`) use the grammar's element object first and fall back to the same scan. In a markup buffer they can disagree (e.g. tags inside `<script>` text). Decide whether `#` should resolve through the element node as well. The element capture spans the whole element, so finding the partner tag needs its child tag nodes or a scan at the span's edge. `#` results on tags would change.
- `llvm-mir` / `llvm-mir-yaml` grammar mismatch — inherited from Helix; no HUME-specific fix until upstream resolves it.
- Snap-vs-error policy for future selection setters — a future selection-setting builtin must handle out-of-range or mid-cluster input from Steel: snap to the nearest valid boundary (forgiving, hides bugs) or raise (fail-fast, breaks legitimately-drifted positions). Decide per call site before the first setter lands.
- `#:keys` activation entry for `declare-plugin!` — would let a lazily declared plugin register its own key bindings as placeholder stubs, the way `#:commands` does today, instead of leaving any plugin whose only entry point is a key it adds or overrides without a manifest, so it loads eagerly (`core:pickers`, `core:vim-keybind`, `core:classic-paste`, `core:helix-surround`). Not pursued yet: the entry would have to restate the body's own `bind-key!` calls in the manifest, a second list to keep in sync, and still couldn't express `unbind-key!` (`core:helix-surround` drops `m w`). Decide based on real usage or user feedback rather than up front.
- Macro registers through `read-register`/`write-register!` — a macro is `Vec<KeyEvent>`, not text, so today both builtins treat a register holding one as empty (`read-register` answers `#f`; there is no write path for one at all). Persistent sessions (see "Editor — new features") covers cross-restart macro persistence natively, reading the register store directly rather than through Steel, so persistence does not need this. What's left is weaker: Steel introspection (e.g. an `:registers`-listing plugin correctly showing "macro recorded here" instead of lying with empty) or programmatic macro composition. Not worth a wire-format decision until one of those is actually wanted.
- Session file scope for registers other than macros — persistent sessions will save recorded macros (decided, see "Editor — new features"); whether numbered registers, the clipboard register (`c`), or the kill-ring register (`k`) are also part of the session file is undecided. Decide when the session format is designed.
- Smart-p and a clipboard changed by another application — a bare `p` reads the kill ring while nothing has been edited since the last capture, and never looks at the clipboard to decide. So `d`, then copying text in another application, then `p` pastes the deleted text instead of the copied one. Emacs avoids this: on each yank it compares the clipboard with the last text it put there, and pastes the clipboard when another application changed it. Decide whether smart-p should also treat a clipboard that differs from the last text HUME wrote or read there as the fresher source. That adds a clipboard read to a paste that today reads only the ring.
- Crashed language server and newly opened buffers — a buffer opened under the same workspace root as a crashed server attaches to it without a message, and its LSP requests then report the crash until `:lsp-restart`. Decide after real-world use whether opening such a buffer should report the crash again, restart the server automatically (and with what backoff), or keep attaching quietly.
