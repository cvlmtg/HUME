# HUME — Roadmap

## Roadmap

Items tagged **[breaking]** change existing user-facing behavior or plugin API when they land.

### Editor — new features

- [ ] Scope-aware local rename — tree-sitter locals, LSP fallback via `core:lsp`.
- [ ] Code folding — tree-sitter-powered collapse/expand.
- [ ] Docked panes — fixed-extent (along the split axis) `LayoutTree` variant alongside ratio-based splits, so a docked pane can be a column as well as a row. `equalize` (which currently rewrites every ratio in the tree on every split/close, see `LayoutTree::Split`'s doc comment) must be scoped to skip docked panes rather than resizing them. Clients: quickfix list, LSP references/diagnostics, embedded terminal/REPL, build/test runner, `:help` pager, DAP debugger views, undo-tree graph (`docs/UNDOTREE.md`). Deferred until the first concrete client is scoped.
- [ ] **[breaking]** Wire remaining bottom-drawer clients — `:ls`, `:messages`, notifications, command/search history pagers onto the existing bottom-drawer primitive. Moving `:ls`/`:messages` off buffers means `buffers` and `on-text-changed` stop seeing them.
- [ ] Wrap indicator — configurable char prepended to continuation display lines in soft-wrap mode.
- [ ] Per-buffer keymaps (Steel) — `on-buffer-enter` already exists to key off of.
- [ ] **[breaking]** `:e` binary / huge-file y/n confirm — binary-sniff + size threshold. The reusable confirm-overlay primitive this needs (`ConfirmLayer`, `hume-editor/src/editor/input_stack/confirm.rs`) already exists, built for the disk-change reload prompt. `:e` and `open-buffer!` would prompt or refuse where they open unconditionally today.
- [ ] **[breaking]** Streaming load for huge files — chunked read replacing single blocking full-file read. `buffer-text`/`buffer-line-count`/`on-buffer-open` could observe a partially loaded buffer.
- [ ] Advertise `completionItem.resolveSupport` (`additionalTextEdits`) — `hume-lsp/src/client.rs`'s `build_client_capabilities()` leaves `CompletionItemCapability::resolve_support` unset, so a conforming server must put `additionalTextEdits` on every completion candidate up front rather than deferring the ones you don't accept; some servers gate whole features (suspected: rust-analyzer's flyimport, offering symbols from modules not yet imported, with the `use` added on accept) behind the client advertising this, rather than just doing it eagerly — unverified against rust-analyzer's own source. Advertising it needs two other changes first: `maybe_send_resolve`'s reply currently drops silently (`hume-editor/src/editor/lsp/drain.rs`'s `stale_check`) if the buffer changed at all since accept, mapped only through the accept edit's own `ChangeSet` — it would need mapping through every edit since, not just that one, or an accepted import can vanish with no message when a server defers it lazily. And `CompletionItem::is_noop_for` (`hume-editor/src/editor/completion/item.rs`) currently treats a no-`textEdit`/no-`additionalTextEdits` candidate matching the typed text as a dropped no-op, reasoning that an LSP item can't be a no-op because a server must front-load edits without this capability — once a server *can* defer them, a fully-typed import-only candidate would be silently hidden by that same check.
- [x] Buffer-words completion source — shipped as `core:buffer-words`, a Steel source (not a native `Buffer`-target `SourceBody` variant — see `docs/COMPLETION-PICKER.md`), deliberately built on the plugin-facing `register-completion-source!`/`completion-emit!` API rather than the Rust-internal machinery the six native minibuffer sources already validate.
- [ ] Styled spans in `show-popup!` — the popup takes one flat string today, so signature help marks the active parameter as `⟨…⟩` on a second line instead of highlighting it in place. Wants a `(start end scope)` span list over the popup text, the shape `set-virtual-lines!`'s `'segments` already uses. Its input already arrives: HUME declares `labelOffsetSupport`, so a server sends each parameter's offsets into the signature label.
- [ ] **[breaking]** Styled spans in the drawer — `lsp-locations->display-parts` shows an unopened target's column as the location's own wire unit rather than a measured grapheme column (see `docs/LSP.md`'s "User-facing column unit" decision row); once a drawer row can style part of itself, render that unmeasured column visually distinctly (e.g. italic) instead of identically to a measured one. Wants the same per-row span support as the `show-popup!` item above. Changes the drawer row / `lsp-locations->display-parts` shape.
- [ ] Auto-generated command reference + in-editor `:help` expansion.
- [x] `:earlier` / `:later` undo-tree time travel — count + relative-age specs over the linear undo/redo path; cross-branch jumps and history-browsing UI remain future work.
- [ ] Persistent undo across restarts — undo history is in-memory only today (`user-manual/docs/files-and-buffers.md`'s "Persistence and safety"); lost on quit, no cross-restart undo. Needs an on-disk format for the undo tree and a load path tied to buffer open.
- [ ] Persistent sessions — save and restore open buffers, splits/tabs, and cursor positions across restarts. **Decided: the session file also records recorded macros** (the `q` register and friends), since they're otherwise unrecoverable after quit and nothing else in the roadmap covers that gap (see Open questions' macro-register item, which this supersedes for persistence purposes). Whether *other* registers (numbered, `c`, `k`) are part of the session file is still open — see Open questions.
- [ ] Steel-side picker row display formatter — `#:truncate 'head|'tail` only picks which end of an over-long row is clipped; see `docs/FUZZY-FINDERS.md`'s "Remaining work" for the general per-row formatter this doesn't cover.
- [ ] **[breaking]** Fully rebindable picker keys — every key a picker handles, `Enter` and `Esc` included, is an ordinary user-overridable binding to a named picker command, beyond the extra keys `#:actions` adds today. HUME ships a default set (candidate home: `core:stdlib`) that users customize, e.g. `2` picks the second candidate, `Tab` marks a candidate in a multi-select picker, `Ctrl-x` clears the query. Moving the defaults into `core:stdlib` leaves a picker without `Enter`/`Esc` for a config that doesn't load it, and changes `#:actions` precedence.
- [ ] Shell filter/insert commands — pipe each selection through a shell command and replace it with the command's stdout (`!` in vim), and run a shell command and insert its stdout into the buffer (`:r !cmd` in vim). Decide whether one command with two modes (a selection present vs. absent) covers both, or two separate named commands.
- [ ] Increment/decrement number under cursor (`Ctrl-a`/`Ctrl-x` in vim) — detect and step the numeric literal at/after the cursor, handling decimal, hex (`0x…`), binary (`0b…`), and octal (`0o…`) forms, preserving the literal's width/padding and prefix.

### Editor — fixes & optimizations

- [ ] Crash-safety net: dump unsaved buffers to disk on panic — a fail-fast invariant firing in production (e.g. `BufferText::char_to_line` once resolved a stale char offset past `len_chars()` to an invalid line, then hardened into a hard panic on that same input) must not take unsaved work down with it. Install a panic hook that writes every dirty buffer to a recoverable scratch path and names the paths on stderr, so the next launch can offer recovery.
- [ ] Lazy grammar attachment — `register-installed-grammars!` (`runtime/scheme/grammars.scm`) runs unconditionally from bundled runtime Scheme, so `attach_grammar` eagerly dlopens and compiles up to 3 tree-sitter queries (highlights/injections/textobjects) per installed grammar at every `init_scripting`. `--no-config` skips `init.scm`, not this — only an isolated `XDG_DATA_HOME` (as `tools/golf/golf.sh` now sets) avoids it. Costs a headless `hume --keys` run highlighting it never renders, scaling with however many grammars are PLUM-installed; would benefit interactive startup identically. Fix: register grammar paths at startup, dlopen + compile queries on first buffer that resolves to that language.
- [ ] Byte-string parsing in settings — `"10MB"` / `"512KB"` strings; companion to the size-threshold setting.
- [ ] Native directory-walker fallback for the file picker — for bare directories without `fd`; build only if the fallback posture proves inadequate in practice (see `docs/FUZZY-FINDERS.md`).
- [ ] `:sort --lexicographic` override — for when numeric auto-detection guesses wrong (e.g. `1.10` vs `1.9`). Not worth shipping until it actually bites.
- [ ] Non-`file:` LSP location URIs (jdtls's `jdt://`, deno's `deno:`) — `goto-location!`/`lsp-locations->display-parts` reject them outright (`hume_lsp::uri::uri_to_path` only understands `file:`); a server sending one is conforming, HUME just has no reader for it yet. The error now names the URI and the unsupported scheme rather than printing `UriError`'s `Debug` form, but the destination is still unreachable.
- [ ] Coalesce repeated scroll events — `run_loop` reads one terminal event and renders, with no batching anywhere on the input path (`viewport_debounce` debounces the `OnViewportChange` hook, not the frame). A held scroll key or a fast wheel delivers events far quicker than a keystroke, and each drives a full `prepare_frame` + render; under soft wrap that formats every visible line per event, since `content_display_lines` formats a line just to count its display lines. Draining consecutive same-direction scrolls and applying them as one motion cuts the *number* of frames rather than the cost of each. Only worth building if held-key scrolling actually measures slow — but if it does, this is the cheaper answer to the problem the line-store cross-frame item under Performance — deferred describes, and should be tried first.

### Performance — deferred

Structural work found during a cheap-wins sweep. Each is real but wants a design decision, an invalidation contract, or a wide signature change — none is a small edit. Nothing here is measured as dominant: the benchmark harness is itself the first item.

- [ ] Criterion benchmark harness over `Editor::render_to_buf` — the workspace has none, so every item below is reasoned from allocation and complexity counts rather than from a profile. Build this before betting on any of them.
- [ ] `Operation::Insert` carrying its own char length — five sites re-derive it with `chars().count()`, and `compose` re-counts a growing accumulator once per keystroke of an insert session (quadratic over the session). Touches every match site on the variant.
- [ ] Frame-level damage tracking — every frame re-formats, re-styles and re-composes every visible display line; only the cell diff in `hume-grid` limits terminal writes. The largest single win and the largest correctness risk (several per-frame sync steps have side effects).
- [ ] Line-store entries surviving a frame — **superseded; kept for the analysis, not as work.** Read the last two paragraphs before picking this up. It is the format-stage third of damage tracking above and would unblock it, but a cheaper fix covers the only case where it could matter. `EngineView::begin_frame` rewinds every pane's `PaneLineStore` unconditionally, so the store shares work only *within* a frame (the scroll step and the render pass) plus with a between-frame command that ran since the last one; across frames its value is zero. A 3-display-line scroll in a 50-display-line viewport discards ~94% of still-valid work, and an ordinary keystroke discards all of it.

  That rewind is a correctness requirement, not hygiene. `update_inlay_hint_providers` and `update_eol_text_providers` (`decoration_providers.rs`) rebuild their per-pane mirrors every frame *filtered to the viewport that frame shows*, and neither bumps `DecorationStores::generation` — so a line scrolling into view gains inline inserts, changing its wrap display-line count, while `FormatKey` sits unmoved.

  The fix is to remove that dimension rather than key on it: make both mirrors unfiltered and generation-gated, exactly as `update_virtual_line_providers` already is via `Editor::virtual_lines_synced`. All three shape-bearing mirrors then become pure functions of `(bid, decorations.generation(bid))`, which `FormatKey::buffer_tag` already folds in, and `begin_frame` demotes from correctness to memory reclamation. Unfiltering is close to free — the LSP publisher sets hints per viewport range, so the store holds roughly a viewport's worth either way — but the change needs an entry-eviction policy designed from scratch, since nothing would rewind the store per frame any more.

  Rejected alternative: putting the mirrors' build window into `FormatKey`. It works, but any viewport move then rewinds the whole store, so scrolling — the case with the most to reuse — never benefits.

  Unmeasured, like everything in this section. The render loop is event-driven and blocks fully when idle (`wake_timeout()` is `None` with nothing scheduled), so frames happen per input rather than on a clock — which is what the budget argument below rests on. Build the harness at the top of this section before betting anything on the numbers here.

  The simplicity cost is concrete: `begin_frame` is the store's only bound today, so demoting it means designing an entry-eviction policy where none exists, and unfiltering the two mirrors widens them from viewport-scoped to whole-buffer — a new cache with a new invalidation contract, which is the category the two `fix(editor)` commits in the original refactor were both about.

  Why superseded rather than merely deferred. One number decides this — the worst-case frame (largest realistic terminal, soft wrap, decorations on) — and both outcomes route elsewhere. Comfortably under a per-keystroke budget: ship nothing, a frame costs a keystroke and the headroom is enormous. Marginal: the problem is not per-frame cost but *sustained* input, and the cheaper answer is the scroll-event coalescing item under *Editor — fixes & optimizations*. Note the budget differs between those two cases and 60fps is the wrong frame for the second: under a held key the constraint is the inter-event interval (tens of events/sec, so ~20ms), and exceeding it shows up as backlog — the view still scrolling after the key is released — not as a low frame rate. A frame-time benchmark cannot see that, which is exactly why the fix is to cut the number of frames rather than the cost of each. Scrolling needs no benchmark of its own: a scroll frame is an ordinary frame, since even `scroll_back_from` walking backward from a distant cursor is bounded by viewport height.
- [ ] One chunk-walking cursor for `display_col_in_line` / `char_pos_at_display_col` — both pay ~6 O(log n) rope descents per grapheme where a single resumable cursor would make them O(line). A grapheme-level sibling of `CharCursor` would do the same for the word motions, which interleave `char_at` with `next_grapheme_boundary`.
- [ ] `Buffer::apply_edit` clones the whole `ChangeSet` per edit (once to record the revision, once into an open group's accumulator) — fine while typing, a full extra copy of the payload on a large paste. `Rc`/`Arc` on the propagated value fixes it structurally.
- [ ] Interning for names cloned per dispatch — `KeymapCommand`'s `Cow<'static, str>` allocates on every dispatch of a Steel-bound key (built-ins are borrowed and free).
- [ ] Statusline recomputes per frame — the `FilePath` two-pass sizing re-renders any section containing it (the default left section), and `DiagnosticsElement` scans the whole diagnostics store for its counts. Both want caching against a generation, not a mechanical fix.

### Plugins

- [ ] PLUM: pin plugins to commit / tag / branch.
- [ ] `core:lsp` `cargo-git` install flavor — installs from a pinned git tag instead of crates.io semver; unblocks `nil`.
- [ ] `core:lsp` install support for `pkg:golang` (gopls) and `pkg:pypi` source kinds — currently fail loudly as unsupported (see `docs/LSP-INSTALL.md`'s "v1 scope and limitations").
- [ ] **[breaking]** Per-buffer plugin exclusion — enable a plugin everywhere except for chosen languages or file patterns, e.g. `core:buffer-words` on for every buffer but `*.min.js`. `declare-plugin`'s `#:languages` only picks what triggers loading; once active, a plugin acts on every buffer. Exclusion therefore has to be checked per buffer each time the plugin would act, not once at activation. Changes when every plugin's hooks, commands, and completion sources fire.
- [x] `:lsp-install` argument completion — a `#:target 'minibuf` source over the installable server names, declared via `define-typed-command!`'s `#:complete`.
- [ ] Color highlighter plugin — inline-highlight hex color literals (`#abcdef`, `#0365AF01`) in a buffer, like `nvim-colorizer.lua`. Needs a new Steel builtin to set a decoration whose background/foreground is computed from arbitrary RGB(A), not one of the theme's fixed scopes.

## Open questions

- **[breaking]** Multiline quote text objects — currently line-bounded (parity scan gives wrong results across unmatched quotes on earlier lines); use tree-sitter to resolve when a grammar is loaded, fall back to line-bounded parity otherwise. `miq`/`maq` results change once a grammar is loaded.
- **[breaking]** `goto-matching-pair` tag matching (`#` on `<tag>`) is a lexical scan, not tree-sitter-backed (`hume-ops` can't depend on `hume-treesitter`). Decide whether it should resolve the enclosing element node once tree-sitter structural navigation lands — same lexical-vs-tree-sitter tension as the multiline-quote question above. `#` results on tags would change.
- **[breaking]** Common-prefix auto-extend on Tab — extend input to the shared prefix of candidates before opening the popup, like readline/bash? Decide after more usage; risks surprising input mutation mid-type. Changes what `Tab` does to already-typed input.
- Plugin-defined languages × lazy loading — a plugin that defines its **own** language must register that identity eagerly; it can't be the sole provider of its own lazy-activation trigger. Deferred to a dedicated brainstorm.
- `llvm-mir` / `llvm-mir-yaml` grammar mismatch — inherited from Helix; no HUME-specific fix until upstream resolves it.
- Search-state clobbering from Steel — no risk today (`search-next`/`select-all-matches` take no pattern arg, can't inject a pattern). Decide guard policy before any future pattern-taking search builtin is added.
- Mark/bookmark drift across edits — a stored char offset goes stale as edits land before it's used. Real marks need positions mapped through edit history; decide where that mapping lives and which stored positions opt in.
- Snap-vs-error policy for future selection setters — a future selection-setting builtin must handle out-of-range or mid-cluster input from Steel: snap to the nearest valid boundary (forgiving, hides bugs) or raise (fail-fast, breaks legitimately-drifted positions). Decide per call site before the first setter lands.
- `#:keys` activation entry for `declare-plugin` — would let a lazily declared plugin register its own key bindings as placeholder stubs, the way `#:commands` does today, instead of forcing `load-plugin` for any plugin whose only entry point is a key it adds or overrides (`core:pickers`, `core:vim-keybind`, `core:classic-paste`, `core:helix-surround`). Not pursued yet: the entry would have to restate the body's own `bind-key!` calls in the manifest, a second list to keep in sync, and still couldn't express `unbind-key!` (`core:helix-surround` drops `m w`). Decide based on real usage or user feedback rather than up front.
- Macro registers through `read-register`/`write-register!` — a macro is `Vec<KeyEvent>`, not text, so today both builtins treat a register holding one as empty (`read-register` answers `#f`; there is no write path for one at all). Persistent sessions (see "Editor — new features") covers cross-restart macro persistence natively, reading the register store directly rather than through Steel, so this is no longer needed for that. What's left is weaker: Steel introspection (e.g. an `:registers`-listing plugin correctly showing "macro recorded here" instead of lying with empty) or programmatic macro composition. Not worth a wire-format decision until one of those is actually wanted.
- Session file scope for registers other than macros — persistent sessions will save recorded macros (decided, see "Editor — new features"); whether numbered registers, the clipboard register (`c`), or the kill-ring register (`k`) are also part of the session file is undecided. Decide when the session format is designed.
- Bare-name stubs for plugin commands — natives already get `(define name (lambda args (%dispatch-command "name" args)))` at startup, so `(move-left)` works without `call!`; `define-command!`/`declare-plugin` could emit the same stub from Scheme via `hm.eval-string` (verified: a `define` evaluated that way from inside a `require`d module lands in engine global scope, visible to every later-compiled plugin), making `(my-plugin/cmd …)` callable directly. Leaning no, or at most as sugar that never replaces `call!`: (1) a bare name is resolved at `require` time — a reference to a not-yet-defined stub is a `FreeIdentifier` compile error for the whole module, even inside a lambda that never runs — so plugin load order turns load-bearing, where `call!` resolves its string at run time and a miss is a logged `#f`; (2) the string namespace is disjoint from Steel globals by construction, while a stub merges them — a forced `<plugin>/` prefix narrows the hazard but doesn't close it, Steel's stdlib has ~116 `/`-containing globals (`call/cc`, `time/sleep-ms`, `channel/recv`, `instant/now`, `any/c`, …), so closing it needs a fail-fast "already bound?" check at stub-define time, not a naming convention; (3) `check_definable` bans only `"` and `\`, so a name that isn't a valid Steel identifier would need rejecting too. `call!` also covers computed names (`(call! (string-append prefix "/" verb))`), which a stub can't.
