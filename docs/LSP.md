Design and shared reference for HUME's Language Server Protocol support (shipped). All LSP decisions live here.

## Overview

**Goals**, in order:
1. **Community-extensible**: LSP features live in Steel so plugins can add features, server integrations, and custom UX without touching Rust.
2. **Snappy on big-realistic workloads**: rust-analyzer on a large crate, 100k-line files, 5k-diagnostic bursts, 1k-item completion lists, large terminals.

**Architecture: Steel on the control plane, Rust on the data plane.** The split is a *frequency cut*, not a per-feature assignment:

- Runs **per user intent** (a keypress-triggered command, a server response arriving, a menu selection) → Steel. A Steel dispatch costs tens of nanoseconds against a 16 ms frame budget (P8 measured ~76ns/call for a registered no-op builtin, 10k calls, release build — includes Steel loop overhead, so real dispatch is at or below that).
- Runs **per frame, per display line scrolled, or over unbounded collections** (rendering, diagnostic bursts, completion filtering, position math over edits) → Rust.

Two structural guardrails keep the experience snappy through the shape of the API, not by discipline:
- **Bulk data never crosses the Rust↔Steel boundary on recurring paths** (per-frame, per-keystroke, per-scroll). Diagnostics and completion items live in Rust-side stores; Steel sees signals, bounded subsets, and policy knobs. A one-time ingest at user-intent frequency (a completion response passing through Steel into the store) is the calibrated exception — confirmed to hold at 1k items (see the Bulk-data guardrail row below).
- **Steel never runs on the render path.** Steel writes data stores; Rust providers render from them every frame.

Rust therefore ships a *platform* — transport, document sync, stores, render providers, a generic LSP bridge, scriptable UI widgets — and the features themselves are Steel code in a `core:lsp` plugin: send request → transform response → call a UI/store builtin. A community plugin author writes the exact same three-line shape.

**v1 feature set**: diagnostics, completions, hover, go-to-definition (+ declaration / type-definition / implementation), rename, references, signature help, formatting, code actions, inlay hints, document and workspace symbol pickers.

**Non-goals for v1**: semantic tokens, snippet placeholder navigation, code lens, DAP.

**Implementation shape** (five macro-steps):
1. **Step 0 — Prerequisites**: workspace groundwork (serde, position mapping, event-loop wake + timers, encodings, URIs, the boundary-cost spike).
2. **Step 1 — LSP core (Rust data plane)**: the `hume-lsp` crate (transport + client) and editor glue (document sync, diagnostics store, registration).
3. **Step 2 — Steel platform**: the generic bridge, codec, stores, edit/navigation primitives, and hooks that let Steel drive everything.
4. **Step 3 — UI surfaces**: scriptable widgets (popup, menu, drawer) and store-fed render wiring (underlines, signs, virtual lines).
5. **Step 4 — Features (Steel)**: the `core:lsp` plugin composing Steps 2–3 into user-facing features.

Steps 1–3 are ordered by dependency but Step 4 tasks unlock incrementally — each feature can land as soon as the primitives it composes exist.

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| LSP architecture | **Hybrid: Steel control plane, Rust data plane** | Rust owns transport, JSON-RPC, document sync, bulk stores, and rendering. Steel owns behavior: every user-facing feature is Steel code composing Rust primitives. The boundary is frequency: per-user-intent work may be Steel; per-frame / per-scroll / unbounded-collection work must be Rust. Maximizes community extensibility without sacrificing latency. |
| Feature delivery | **Generic LSP bridge + `core:lsp` plugin, not hardcoded Rust features** | `(lsp-request! pane method params callback)` / `(lsp-request-all! …)` / `(lsp-notify! …)` / the `on-lsp-notification` hook make any protocol method reachable from Steel. v1 features ship as the `core:lsp` plugin using the same public surface plugins get — dogfooding guarantees the bridge is complete. Rust volume is similar to hardcoding v1 (generic infra costs more up front), but marginal feature cost afterward is a Steel file anyone can write. |
| Bulk-data guardrail | **Bulk never crosses the boundary on recurring paths** | Diagnostics are ingested, stored, and remapped in Rust; Steel receives change *signals* and pulls bounded subsets (visible lines, top-N). Completion items live in a Rust store with a Rust per-keystroke filter; Steel orchestrates and sees the top-N. The one crossing allowed is a per-user-intent ingest — `core:lsp`'s completion source, which never reads a field of the response itself, sends it through as one opaque `lsp-request!` handle (see the row below) rather than the general per-keystroke case this guardrail is really about. |
| `lsp-request!` result representation | **Every response crosses as one opaque `JsonHandle`, never a full decode into hashmaps/lists** | Applies uniformly to every LSP-shaped crossing: `lsp-request!`'s response, `lsp-capabilities`, `diagnostics-for-buffer`'s `'raw` field, the `on-lsp-notification` hook's params, `on-completion-accept`'s item, and `json-parse`. `json-ref`/`json-ref-or`/`json-contains?`/`json-list`/`json-array?`/`json-object?` (`hume-scripting/src/builtins/json.rs`) are the Steel-facing accessors every one of them reads a handle through. `null` still crosses as `Void`, so every feature's existing `(void? result)` check for "server declined" stays meaningful; a scalar top-level value (only reachable via `json-parse`, never an LSP response) crosses natively rather than as a handle. A response handle also carries its producing server's negotiated encoding — every child a `json-ref`/`json-list`/`json-ref-or` navigation pulls out of it inherits the same tag, so `goto-location!`, `apply-workspace-edit!`, `apply-text-edits!`, and `lsp-label-offsets->text`/`lsp-locations->places` each read the encoding straight off the value in hand instead of resolving it from a caller-supplied `pane`'s *currently* attached server (which could have since restarted or detached). A `json-parse` result or a hashmap a plugin builds by hand carries no such tag, so those builtins error on one rather than guessing an encoding. |
| Render decoupling | **Data-driven decoration stores; Steel never on the render path** | Steel setters (`set-inlay-hints!`, `set-signs!`, `set-virtual-lines!`, …) write Rust-side stores; the engine's `DecorationSource` trait (unifying the former `HighlightSource`/`VirtualLineSource`/`InlineDecoration`, plus `SignSource` separately) renders from them each frame with zero Steel involvement. |
| UI widgets | **Rust-rendered, Steel-fed** | Cursor popup, selection menu, drawer list are generic Rust widgets taking content + callbacks from Steel (`show-popup!`, `show-menu!`, `show-drawer-list!`). LSP is their first client, not their owner — any plugin can use them. |
| Symbol rename | **LSP-only in v1** | `textDocument/rename` via `core:lsp`; an unattached buffer reports unsupported through the capability guard. A tree-sitter local-rename fallback (file-local, via `locals.scm`) is out of core:lsp's scope — a separate feature to design later, not part of this plugin. |
| Position remapping through edits | **Batch `PosMapCursor`, never per-position** | Diagnostic ranges, bookmarks, and any stored positions must be remapped through edits with the batch primitive: `ChangeSet`'s public `PosMapCursor` (`hume-editing/src/changeset/mod.rs`) maps sorted position lists through one cursor. Per-position one-shot mapping is O(positions × ops). |
| Protocol types | **`lsp-types` crate** | De-facto standard (rust-analyzer ecosystem), spec-tracking, serde-based. Hand-transcribing the LSP spec is weeks of error-prone tedium. |
| Transport concurrency | **std threads + mpsc; `LspBackend` trait mirroring `ParseBackend`** | Per server: reader thread (blocks on server stdout), writer thread (stdin), stderr logger. Messages cross to the main loop via mpsc; `prepare_frame` drains; the reader/stderr threads wake the main loop directly via a cross-thread `WakeCallback` after posting — byte-for-byte the `ThreadedParseBackend` pattern. No tokio: transport concurrency is never the bottleneck (heavy JSON parse lands on reader threads off the main loop; incremental `didChange` is proportional to the edit, not the file), and a runtime would split a fully-sync codebase into two concurrency idioms. The trait boundary is the insurance policy. Cost accepted: request timeouts are hand-rolled (deadline check at drain time). |
| Crate boundary | **New `hume-lsp/` crate** | Follows the `hume-treesitter` precedent (zero `Editor` dependency, acyclic). Full rationale: `hume-lsp/src/lib.rs`'s module doc. |
| Server instance scope | **One per (registration name, workspace root)** | The first buffer whose language plans a server spawns that server for the buffer's resolved root; a later buffer of any language whose list names the server, under the same root, attaches to the same process. The root resolves from the buffer's language's root markers (`LanguageRegistry::roots_of`, `RootCache::root_for`); a language with none resolves to the cwd. Correct `rootUri` when two projects share a session; the diagnostics store keys by server. |
| Position encoding | **Negotiate `utf-8`, fall back to UTF-16 conversion** | LSP defaults to UTF-16 code-unit columns; 3.17's `positionEncoding` capability lets client and server agree on `utf-8`. HUME is char/grapheme-based, so both paths need conversion helpers; ropey 1.6 provides `char ↔ utf16_cu` primitives (`char_to_utf16_cu` / `utf16_cu_to_char`, unconditional — no feature flag in 1.x) for the fallback. Never assume byte == column. |
| Timers | **Timer wheel in the event loop; `(after! ms thunk)` + debounced hooks in Steel** | The loop already degrades to `poll(timeout)` when async work is pending; a nearest-deadline timer wheel bounds that timeout naturally. Required for debounced inlay-hint refresh, signature-help triggering, and completion debounce — without it, scroll- and keystroke-driven Steel work would fire unthrottled. |
| Server→client requests | **Answered in Rust, never surfaced to Steel in v1** | JSON-RPC requires a response to every request, including server-initiated ones. C6 dispatches them: `workspace/configuration` answered from C8 settings, `workspace/applyEdit` applied via the B6 engine, `client/registerCapability` / `window/workDoneProgress/create` acknowledged and ignored, anything else gets a `MethodNotFound` error response. Steel handles notifications only (the `on-lsp-notification` hook) — response obligations stay where timeouts can't be caused by a plugin. |
| Diagnostics exposure granularity | **`diagnostics-for-buffer` caps at 1 000 items** | Measured JSON→SteelVal conversion (steel-core's built-in `IntoSteelVal for serde_json::Value`) at 100/1k/5k diagnostic-shaped items, release build: ~86µs / ~750µs / ~4.2ms. Confirms the hub's 1 000 default with comfortable margin. `core:lsp` pulls a buffer's diagnostics on every publish, so the cap bounds that pull too, not only one the user asks for. Filtered by the optional `#:severity` / `#:range` arguments before the cap applies; the first 1 000 by position are kept, and a trace notes a read the cap cuts, once per buffer and floor until a whole-buffer read at that floor is under the cap again. |
| Pull diagnostics | **A server is asked for its diagnostics with `textDocument/diagnostic` only until it first sends `publishDiagnostics`; the client does not declare `textDocument.diagnostic`** | `vscode-eslint-language-server` has no push path at all, while `rust-analyzer` advertises `diagnosticProvider` and also pushes, so the capability cannot say which a server does. A server that offers both stops pushing once the client declares pull, so the client leaves it undeclared and observes instead: `Instance::pushed_diagnostics` latches on the first publish, and a pull answer landing after it is dropped. `workspace.diagnostics.refreshSupport` is declared so a pull-only server can ask for a re-pull. A pull goes through `EditorState::lsp_request_json`, routed by method, so the `pull-diagnostics` feature filter and the `diagnosticProvider` capability gate it like any request, and its report reaches the same `EditorState::store_server_diagnostics` funnel a publish does (`lsp/pull.rs`). The last report's `resultId` rides on the buffer's attachment (`previousResultId` on the next pull), so detach and close drop it. Triggers: attach, a text change debounced per buffer (`lsp-diagnostics-pull-debounce-ms`), `didSave`, and `workspace/diagnostic/refresh`. A report's `relatedDocuments`, `workspace/diagnostic` and a dynamically registered `diagnosticProvider` are not handled. |
| Steel completion scorer budget | **Re-rank Rust's top-N only (N = 64)** | This is architectural, not just a speed call: per-item conversion/iteration cost is low (~0.8–1µs/item) but completion filtering runs *per keystroke* — the hub's frequency-cut rule (recurring paths must be Rust, regardless of measured Steel throughput) means an unbounded Steel scorer would violate the guardrail even though it would be numerically affordable at 1k items. Bounded top-64 re-rank confirmed as the default. |
| LSP idle wake | **Cross-thread waker, no poll cadence** | The LSP transport threads signal the main loop's wait primitive directly after posting a result, so `LspState::next_wake` reports real deadlines only (the earliest pending-request deadline, plus the statusline spinner's cadence while Starting/`$/progress`). |
| WorkspaceEdit on unopened files | **Open-as-buffer** | Rename/code actions can touch files with no open buffer. Chose open-as-buffer (undoable, dirty, user saves via `:wa`) over a direct fs write (atomic but bypasses undo) — consistent with every other HUME mutation going through the undo tree. `apply_workspace_edit` validates every file first (opening unopened ones along the way) and only commits once all have passed, then reports `"N buffers modified — :wa writes all"` (`"1 buffer modified"` for one) on the status line, for a script's call and a server's `workspace/applyEdit` alike; an edit with nothing to apply reports nothing. |
| `set-extra-highlights!` tier | **New variant `Extra` between `Syntax` and `SearchMatch`** | Plugin spans beat syntax, lose to search/diagnostics/brackets. See `HighlightTier`'s doc comment in `hume-engine/src/providers.rs` and `TIER_COUNT` in `hume-engine/src/style/highlight.rs`. |
| `$/progress` | **Message-log only in v1** | No spinner element added — the statusline's only new element is `Diagnostics` (error/warning counts). `$/progress` routes to the message log via the existing server-notification handling; a spinner element is Future. |
| Hover surface (revised) | **Popup only — cursor or docked layout, never the drawer** | `show-popup!`'s ⅓-pane-height max is the threshold for the cursor layout. Content taller than that docks instead (`#:anchor 'bottom`): a full-width band above the statusline that reserves pane space like the drawer, but keeps popup semantics (plain scroll, no selection) — hover overflow is not a pick-list, so it never uses `show-drawer-list!` (which stays references/goto/diagnostics-only). Rust never chooses between the two layouts — it's a Steel-side branch on formatted content length, same as before. |
| `set-hook-triggers!` context | **Relaxed to any context, no init/plugin-load gate** | Servers register their trigger characters from inside their `on-lsp-attach` handler, which runs as plain command context — the previous init-only gate made this uncallable. No feature needs init-time registration, so the gate was dropped entirely rather than widened to "init or command." |
| Per-range formatting fan-out join | **Hand-rolled in Steel (`lsp/format-fan-out!`), not a Rust primitive** | The `rangeFormatting`-per-range fallback joins N requests to one server (`#:to`, the first with range formatting) with a `pending` counter, an `edits` accumulator, and an `aborted` flag, all in `format.scm`. A delivery (row "Deliveries") joins one request sent to several servers; this join is several requests to one server, a different shape with this one caller. A second caller needing it is the point to add a Rust primitive beside deliveries in `lsp/bridge.rs`. |
| Steel settings read access (revised) | **`(get-option key)` (global only) and `(get-buffer-option pane key)`, symmetric with `set-option!`/`set-buffer-option!`** | Multiple features need to read a setting from Steel (e.g. `indent-width`/`indent-style` → `FormattingOptions`); no getter existed. The original single `(get-option [pane] key)` builtin defaulted an omitted `pane` to the focused buffer — an ambient-focus read with the same wrong-buffer hazard as `(current-buffer)` inside an async callback, so it was split: `get-option` never resolves a buffer override at all, `get-buffer-option` always requires one explicitly. `hume-editor/src/settings.rs`'s `setting_value` covers every `global`/`buffer`/`subfield` macro-declared key, plus the hand-written `manual_keys` entries (`statusline`) — `whitespace-*` round-trips through its own generated `subfield` arm, not through `manual_keys`. Every `from_str`/`enum_str` setting type implements `SettingText` (`parse`/`to_text`/`VALUES`), so one generic accessor round-trips them all. |
| Completion accept/refilter Steel visibility | **`on-completion-accept` hook; `isIncomplete` re-asks the source, no hook; `CompletionItem` retains the raw response item** | `on-completion-accept (pane item)` is queued once the accept's own edits (main edit + any `additionalTextEdits`, one undo step — see the row below) have landed, before any `completionItem/resolve` is sent, so a resolve response's edits land after it; `item` the accepted item's full raw JSON, as a `JsonHandle` (read with `json-ref`); a plain extension point now, not Steel's job to apply anything further. A source whose answer said `isIncomplete` is simply *called again* by the editor on the next keystroke (`EditorState::reconcile_completion`, `hume-editor/src/editor/completion/orchestrate.rs`) — bounded to the one case that needs it, not an unconditional per-keystroke hook (which the hub's frequency-cut rule would forbid), and with nothing for the plugin to subscribe to. |
| `additionalTextEdits`/`completionItem/resolve` ownership | **Rust owns the accept, as one undo step** | `BufferSession::accept` (`hume-editor/src/editor/completion/session/accept.rs`) decodes the main edit and any `additionalTextEdits` against the document the completion request was made on and maps both forward through every keystroke since (`cs_since`; the additional edits through `edits::build_edits_from_earlier_document`), so each lands where the server meant it. It commits the additional edits first (`edits::commit_char_edits`), then the main edit around each cursor, inside one edit group, so a single undo takes both back. When the accepted item's own source declared `#:resolve #t` at registration (`BufferSourceEntry::resolve` — a source's claim that its items are the buffer's server's own wire items, not merely that a server happens to be attached; `core:lsp`'s only current declarer), the item lacks `additionalTextEdits` entirely (not just an empty array), and the server advertises `resolveProvider`, accept sends `completionItem/resolve` once its edits have landed, and the response arrives asynchronously (through the same delivery and anchor machinery every `lsp-request!` uses, so `:lsp-stop`'s `drain_pending` teardown sweeps it for free). The response's positions are decoded against the pre-accept rope, mapped *forward* through the accept's own composed `ChangeSet` (`build_edits_from_earlier_document`, `ChangeSet::map_ranges`) onto the buffer as it now stands, and committed as an edit of their own. Without the source's own flag, a second `Buffer` source sharing an LSP-attached buffer (`core:buffer-words`) would have a resolve request sent for an item the server never produced. |
| Inlay hints default | **Off; `core:lsp`'s `#:config 'inlay-hints` sets the start state, `:toggle-inlay-hints` flips one buffer** | Off-by-default. |
| `workspace.workspaceEdit` client capability | **Declared: `documentChanges`, `resourceOperations` (create/rename/delete), `failureHandling: Abort`** | Without this declaration servers refuse `textDocument/rename` outright. See `resource_operations` in `hume-lsp/src/initialize.rs` for why it must stay non-empty specifically. |
| Wire codec null-result handling | **`hume-lsp/src/codec.rs`'s `result`/`error` distinguish "field absent" from "field present as JSON `null`"** | A spec-valid `{"id":N,"result":null}` response must not crash the connection. Full rationale: `codec.rs`'s doc comment on the field. |
| `map_ranges` on nested/overlapping ranges | **`hume-editing/src/changeset/mod.rs`: ends walked via an index permutation sorted by end value, not input order** | `ChangeSet::map_ranges` asserts its input sorted by *start*, but ends aren't necessarily non-decreasing in that same order for *nested* ranges (e.g. two LSP diagnostics on the same span). Full rationale: `map_ranges`'s own doc comment. |
| `textDocument.codeAction` client capability | **Declared: `codeActionLiteralSupport` (quickfix/refactor/source kinds), `isPreferredSupport`, `disabledSupport`** | A server withholds diagnostic-derived quickfixes entirely without this. See `code_action_literal_support` in `hume-lsp/src/initialize.rs` — found via manual smoke testing against rust-analyzer. |
| `diagnostics-for-buffer`'s `raw` field | **Each entry's `'raw` key is an opaque `JsonHandle` onto the original wire `Diagnostic`, not a decoded hashmap** | `textDocument/codeAction`'s `context.diagnostics` must echo back the *raw* diagnostics currently shown in the request range — servers gate diagnostic-derived quickfixes on this, treating an empty array as "the client isn't showing any diagnostics here." `StoredDiag`'s `raw: Arc<serde_json::Value>` field is the wire `Diagnostic` exactly as the server sent it (`hume-lsp` pairs each parsed diagnostic with its wire value), so fields `lsp_types` does not model survive the echo; `diagnostics-for-buffer`'s builtin (`hume-scripting/src/builtins/decorations.rs`) hand-builds its result hashmap field-by-field so `'raw` alone crosses via the same `Arc`, not `json_to_steel`'s deep decode. `actions.scm` extracts it and hands it straight back as `context.diagnostics`, no position math and no reconversion in Steel. |
| Snippet completions | **Strip to plain text, Rust-side** | `insertTextFormat == 2` items get `${n:default}` rewritten to `default` and bare `$n` dropped at store ingress (see `strip_snippet` in `hume-lsp/src/completion_item.rs`) — no choices, no nested placeholders, no `\$` escapes. `raw` keeps the pristine snippet text for `completionItem/resolve`. Full snippet support (tabstop navigation) stays Future. |
| Multi-character inline inserts | **`hume-engine/src/format.rs`: one `Grapheme`/`Cell` per grapheme cluster of the insert text, not one cell for the whole string** | The frame holds one cell per terminal column; text wider than one cell must be split into one `Cell` per grapheme or its spillover gets overwritten. Full rationale: `push_virtual_cells`'s doc comment (`hume-engine/src/format/virtual_cells.rs`). |
| Server crash policy | **Manual `:lsp-restart [name]` only — no auto-restart** | A crashed instance keeps its buffers attached: routing skips it, a buffer opened under the same `(name, root)` joins it rather than spawning a fresh process, and the crash is reported once, when it happens. `:lsp-restart` stops it and reconciles its buffers, which spawns a fresh instance (`apply_lsp_server_ops`, `hume-editor/src/editor/lsp/attach.rs`). A stop is durable: the `(name, root)` instances it ended are marked (`LspState::stopped`), and `lsp_reconcile_one` drops a marked server from what a buffer wants, so a registry change or a new buffer does not start it. `:lsp-restart`, a `register-lsp-server!` or `unregister-lsp-server!` of the name (`LspState::forget_stopped`) and `reset_config` clear the mark, so `:reload-config` starts a stopped server again. `:lsp-status` lists the marked servers. The mark is per root, so a stop aimed at one buffer leaves the same server running for another root. |
| `workspace/configuration` flow | **`register-lsp-server!`'s `#:settings` blob pushed once as `didChangeConfiguration` after `initialized`, and resolved per-item (dotted `section` walked into the blob — VS Code semantics: no section returns the whole blob, a miss returns `null`) to answer `workspace/configuration` pull requests** | The push lives in `hume-lsp/src/client.rs` and resolution in `hume-lsp/src/server_request.rs` (`resolve_config_section`, `workspace_configuration_response`); the editor glue resolves the requesting server's own config in `hume-editor/src/editor/lsp/drain.rs`'s `ServerRequest` dispatch arm. A miss is expected and harmless; see `docs/LSP-INSTALL.md`'s "Config delivery & per-server audit" section for the per-server audit. |
| Registration identity | **A registration name, ranked by whose behalf it is made; last-wins per name within one rank.** `(register-lsp-server! name #:command …)` replaces the config of an already-registered `name`, rather than rejecting the second call, unless a higher rank made that registration, and `unregister-lsp-server!` follows the same rule. A registration made on the user's behalf (`init.scm`, a command the user runs, and what that command schedules) ranks above a plugin's own (its body and hooks), which ranks above HUME's runtime files (the registry's `Ranked<_, ServerRegistrationTie>` slot, whose `write`/`clear` the registry's own `register`/`unregister` call and whose `Claim` `lsp-server-registered?` replays the queued ops on). | The user must be able to override a plugin's registration in either order: a lazily activated plugin runs after `init.scm`, or during it when another plugin's top-level `call!` activates it, so evaluation order cannot decide. A command the user runs, `:lsp-install` among them, is the user's choice for the session, as `:set` is; `init.scm` applies again at the next start. Within one rank last-wins keeps a reinstall's unregister-then-register working. Running instances keep the config they were spawned with until their next spawn, and a registration that differs from it is reported once at Warning (`report_config_drift`, `lsp/attach.rs`); a caller needing a fresh spawn unregisters first, and may register again in the same eval: the unregister stops the name's running servers where it falls among the eval's ops. Every op is queued and applied by `Editor::apply_lsp_server_ops` at the end of an init eval or a command/hook body, and a lazy plugin activation applies its own registration synchronously, so the buffer that triggered it attaches in that same call. The registry (`lsp/registry.rs`) is pure policy: names, configs, per-language lists, no process state. |
| Per-language server list | **A language's servers are the registered entries of the list the highest origin set, in the highest tier that has one** | `Registry::plan` derives a language's ordered servers on each call and stores nothing. A language keeps two tiers of lists, explicit and default, each with one list per `ConfigOrigin` (`ListTier`): `set-language-servers!` writes the explicit tier as the caller's origin (`SteelCtx::registration_origin`), and `set-default-language-servers!` writes the default tier, which applies only while no explicit list is set, so the defaults `:lsp-install` writes on the user's behalf never beat anyone's explicit list. Within one origin the later list replaces the earlier, `#f` clears only the caller's, and one list per origin keeps the result independent of call order: a plugin activated after `init.scm` cannot replace the user's list, and clearing the user's lets the plugin's apply again. A registration says only how to launch a server, so a registered server that no list names serves no language, and a list may name any registered server for any language. An entry may carry `only-features`/`except-features` (`FeatureFilter`, `hume-core/src/lsp.rs`, 21 feature names). An entry naming a server that is not registered is kept and takes effect when it registers (plugins register lazily). `core:lsp-install` writes the default list of every catalog language at load. |
| Attachments and instance lifetime | **A buffer's attachments are a function of its language, path, the registry and the lists; an instance lives while some buffer is attached** | `EditorState::lsp_reconcile_buffer` (`lsp/attach.rs`) recomputes a buffer's attachments from those inputs and is called from the input chokepoints only: a language change (`set_buffer_language_impl`), a path change (`Editor::set_buffer_file`), a registration/list op, `:lsp-restart`, and `:reload-config`'s resync. It detaches with `didClose` what the plan no longer names, attaches with `didOpen` what it lacks, updates a kept attachment's feature filter in place, and orders attachments as planned. Each document records the `languageId` and URI its servers opened it under (`OpenedAs`, `lsp/document.rs`); a language or path change that alters either closes the document under the old one and reopens it under the new one, on the same instances. Detaching the last buffer of an instance stops it at the end of the same call; there is no reaper and no crashed-server tombstone. A buffer close detaches its servers without firing `on-lsp-detach` (`on-buffer-close` announces it). |
| Document sync fan-out | **One queue of changes per attached buffer, encoded per server at flush time** | `LspDocuments` (`lsp/document.rs`, owned by `BufferPositions`) holds a buffer's attachments and the changes not yet sent; it exists only while the buffer has an attachment. `PositionStores::carry` records every non-identity change into it, so every text mutation, `:e!` included, reaches the servers through `Buffer::install`. A flush takes the queue once and sends each server its own form: ranged events in its encoding for `INCREMENTAL`, one whole-document event for `FULL`, nothing for `NONE`. A buffer is flushed before an attachment is added or removed, so a new server never receives a change older than its `didOpen` text. `didSave`/`didClose` go to every attached server. |
| `(declared-plugins)` scope | **Reports every declared plugin, `core:*` included** | Generic introspection, not scoped to any one consumer. `plum/missing-plugins` (`plugins.scm`) is where the never-install-core filter belongs — core plugins being un-installable is PLUM's install-list policy, not a property of what `init.scm` declared, so it filters `core:*` back out locally rather than the builtin doing it globally. |
| Supersede-cancel for `lsp-request!` | **Explicit opt-in `#:supersede <key>` on `lsp-request!`/`lsp-request-all!`** | A new request with `#:supersede k` cancels the delivery still in flight under `k`, on every server it went to, and its callback never runs (mechanism: `EditorState::lsp_send_request`, `lsp/bridge.rs`). A key is an opaque `SupersedeKey` from `(lsp-supersede-key)`, never a string: a string namespace is shared by every plugin and by the editor's own documentation resolve, so a reused name cancels someone else's request. The editor files its own requests under `EditorDeliveryKey`, which no script can name (`DeliveryKey`). The key alone names it: routing picks the servers at send time, so a key per server would let a request routed elsewhere leave the old one running. **Never automatic by method name** — that would silently cancel two features' concurrent same-method requests (e.g. two plugins both calling `textDocument/hover`) that were never meant to race each other; explicit opt-in keeps the policy in Steel, where it belongs. |
| Routing at send time | **Steel states the policy, Rust picks the servers when the request is sent** | `lsp-request!`/`lsp-request-all!`/`lsp-notify!` take `#:feature` (a feature name, for a method with no standard feature of its own: naming one for a standard method raises at the call); `lsp-request!` and `lsp-notify!` also take `#:to` (a server value); a standard method implies its feature, and the one capability it needs where its feature spans several (`requirement`, `lsp/features.rs`), for a notification as for a request. `route` (`lsp/route.rs`) applies them to the buffer's attachments, in attachment order, at the moment the request goes out: running servers only, whose list entry admits the feature and whose capabilities advertise it (`lsp/features.rs`). A server value a plugin picked earlier never decides routing on its own, so a choice made before an async boundary (a prompt, a debounce) cannot go stale; `#:to` is for a follow-up that must reach the server an earlier answer came from. A request no server can take calls back at once with the reason. |
| Deliveries | **One request to N servers is one delivery with N slots** | `EditorState::lsp_send_request` (`lsp/bridge.rs`) serializes the params for each routed server and files each answer in its slot; the callback runs once, when the last slot fills (answer, error, timeout, or a stop that drains the server). `lsp-request!` sends to the first routed server and calls back `(err result)`; `lsp-request-all!` sends to all of them, or to the servers its `(server . params)` pairs name (a non-empty list, each server once; when none of them can take the request it calls back unavailable, like a request no server can take), and calls back `(err results)`, one `(hash 'server 'err 'result)` per server in order. Every `err` is `(hash 'kind 'message)`, plus `'code` for a server's own error: `'server`, `'timeout`, `'stopped` (the server stopped or crashed before it answered), `'unavailable` (no server could take the request, or a named one is not attached and running) or `'unsent` (the params could not be serialized for that server), so a caller tells a setup with no capable server from a failure (`SlotError::into_steel`). The anchor check (`#:allow-stale`, `#:require-focus`) applies to the delivery as a whole. |
| Opaque positions | **HUME-built positions stay opaque until serialized for a server** | `lsp-position-params` and its siblings return the document URI with a `DocPos`/`DocRange` value (`hume-scripting/src/builtins/ids.rs`) in place of a wire position, since a buffer's servers may count columns in different encodings. The bridge encodes each one in the routed server's encoding when it serializes the params (`serialize_params`); a position from another buffer, or one taken at an earlier text version of its buffer (an edit in the same eval, say), fills that server's slot with an error: each carries the `TextVersion` it was built at. Any other JSON-taking builtin rejects such a value. |
| Fan-out vs pick-first per feature | **A feature whose answers combine asks every server; one whose answers conflict asks one** | `core:lsp` sends completion, code actions, goto, references, the locations refresh, inlay hints and the document and workspace symbol pickers with `lsp-request-all!` and merges: completion items join in one menu (`completion-emit!` takes each server's response as an entry), code actions list `(server . action)` with the server's name appended only when two or more servers offered some, locations go through `lsp-locations->places`, or `lsp-locations->merged-places` where only the places to show matter, which keeps the first row naming each path, line and column and hints append. Hover, signature help, rename and formatting edit or show one thing, so they go to the first server that supports the feature. Each server's code-action request carries only the diagnostics that server published (`'server` on `diagnostics-for-buffer` entries), and an action's resolve and command go back `#:to` the server that offered it. |
| Trigger characters per attachment | **A server's trigger characters live on each buffer's attachment to it** | `set-hook-triggers!`/`set-completion-triggers!` take a language name, kept in the language's `TriggerTable` (`ConfigState::triggers`, `triggers/table.rs`). `set-attachment-hook-triggers!`/`set-attachment-completion-triggers!` take a pane and a server value, kept on that buffer's `Attachment` (`lsp/document.rs`) and gone when it detaches. A keystroke's sources are the union of its buffer's language table and its attachments' tables (`EditorState::triggered_by` in `triggers/mod.rs`, which returns hook listeners in name order and completion sources in registration order). `core:lsp` registers each attachment's characters from `on-lsp-attach`, and the editor keeps a set only when the attachment's list entry admits the set's feature and the server advertises it, so a trigger exists only where its feature is handled and no feature checks again when it fires. A change to the attachment's filter empties its tables and fires `on-lsp-attach` again; `:reload-config` empties every attachment's tables and the resync fires it. A table kept per server instead would serve every buffer attached to that server whatever each buffer's own list says. |
| LSP server lifecycle ownership | **`core:lsp-install` owns install, uninstall and installed-server registration; `core:lsp` owns the client and runtime management (`:lsp-status`/`:lsp-stop`/`:lsp-restart`); `core:plum` is not involved** | The two meet at the editor registry (`register-lsp-server!`, by server name), so the installer is replaceable without touching the client. See `runtime/plugins/core/lsp-install/docs/architecture.md` and `docs/LSP-INSTALL.md`'s "Placement" and "Registration model" sections. |
| `steel-language-server`'s host-globals reach | **A shipped, generated file + `register-lsp-server!`'s `#:env`, not a runtime write** | `steel-language-server` (registered by `core:steel-server`) learns HUME's own Steel identifiers only by finding a `(#%register-global "name")` file in the directory named by `$STEEL_LSP_HOME` at its own startup — no CLI args, no `initializationOptions` channel exists for this. `runtime/plugins/core/steel-server/lsp-home/hume-globals.scm` is generated from `ScriptingHost::host_global_names` (diffed against a pristine engine to drop upstream Steel stdlib names, then filtered against `is_internal_name` — `%`-prefixed private primitives, `*earmuffed*` internal state, `hm.`-prefixed `steel/meta` aliases, `#`-prefixed steel-core internals, and the `struct:NAME` descriptor and `___NAME-options___` hash steel-core's `struct` macro binds beside every struct — so the file only lists names a plugin author could actually type) and checked in; `hume-editor`'s `hume_globals_scm_matches_generated_host_names` test fails the build if it drifts. The plugin points `#:env '(("STEEL_LSP_HOME" . dir))` at that directory, gated on `hume-globals.scm` itself existing inside it (not just the directory) — the server's `read_dir` on a missing `$STEEL_LSP_HOME` panics at startup with no fallback, so the existence check is what keeps the server from crashing on launch. |
| LSP default keybindings | **All bound by `core:lsp` itself (`bind-key!` in `plugin.scm`), none in Rust's native default keymaps** | With no `core:lsp` loaded or declared, none of its keys exist at all — no post-init keymap lint warning, no dead binding. See `runtime/plugins/core/lsp/README.md`. |

| Virtual-line-aware scroll/cursor math | **Landed end to end, both wrap modes** | `hume-engine/src/display_lines.rs`'s `DisplayLineMap` owns the display-line list, and every consumer reads it: `cursor::content_pos`/`screen_to_cluster`, `Viewport::reveal`/`align`/`heal` (`hume-engine/src/display_lines/scroll.rs`), `mouse.rs`'s wheel scroll, `visual_move::move_vertical`, and `pane_render::render_pane` itself. | Wire `languageId` vs HUME's language name | **Per-language override in the registry's per-language configuration, set by `configure-language!`'s `#:language-id` or filled from the language's bundled data file, defaulting to the name** | HUME's language names diverge from the LSP spec's well-known document identifiers for a handful of languages (`tsx` needs `typescriptreact`, `jsx` needs `javascriptreact`, etc.) — sending the bare name made validating servers (e.g. `typescript-language-server`) log an "Invalid languageId" warning and silently correct it. `scripts/sync-grammars.py` carries the `language-id` key into `runtime/scheme/languages/<name>.scm`; `lsp_did_open` (`sync.rs`) reads `LanguageRegistry::lsp_language_id_of`, never `name_of`. |

| User-facing column unit | **Grapheme column everywhere a buffer is open; the location's own wire unit otherwise, as a documented exception** | The 2026-08-22 column-naming sweep made every internal identifier kind-explicit but left the *displayed* value alone; `:diagnostics` rendered a char column, the goto/references drawer rendered a raw wire `character` (UTF-16 code units), and the statusline a grapheme column — three different numbers for one cursor position on any non-ASCII line. Grapheme column wins because it's already what the statusline shows and what the editing model itself counts in (`grapheme_col_in_line`'s doc: "matches how many times the user pressed →"). `diagnostics-for-buffer` returns `start-char` (addressing, the `'char-offset` `goto-location!` takes) and `grapheme-col` (display). The goto/references drawer initially resolved an unopened target's column the same way, reading its file from disk once per distinct path — synchronous, uncapped, on the frame loop, to refine one number for a row the user might never select. That was rejected as disproportionate: `(lsp-locations->places locs)` (`hume-editor/src/editor/lsp/introspect.rs`'s `location_places`) now reads no file at all — an open buffer still gets an exact grapheme column, but an unopened target's row shows the location's own wire `character` verbatim, diverging from the true grapheme column only when non-ASCII text precedes it on the same line. This is the one sanctioned exception to "wire `character` and `char-col` are never rendered directly"; it is not open to reuse elsewhere. |
| Malformed-location vs no-place degrade | **Abort the whole `lsp-locations->places` batch on a location missing `uri`/`range`; leave out a location with no place to jump to** | The drawer's `on-select` *is* `goto-location!` — a location missing `uri` or `range.start` names no destination at all: a malformed answer, which aborts loudly. A well-formed location with no place to jump to — a non-`file:` URI (a server HUME can't open, e.g. jdtls's `jdt://`), or a line past the content of the file's open buffer (a stale answer) — is `#f` in `lsp-locations->places` and left out of `lsp-locations->merged-places`, which counts it, so every listed row can be selected. The stale-line check is the one `goto-location!` jumps with (`wire_to_cluster`). An *unopened* target's file is not read (per the row above), so its stale line still lists; selecting it makes `goto-location!` answer `#f`, which `core:lsp`'s `lsp/jump-to!` reports as a warning. Both builtins decode through the one shared `hume_lsp::location::decode_location` (`hume-lsp/src/location.rs`). Handed a non-`file:` URI directly, `goto-location!` raises with the URI and the unsupported scheme rather than `NotFileScheme`'s `Debug` form. |

## LSP protocol primer

Compact model of the protocol as HUME uses it. Full spec: <https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/>. The `lsp-types` crate mirrors the spec's type names — when this doc names a protocol type, that's the `lsp_types::` type.

**Wire format.** Each message is `Content-Length: N\r\n\r\n` followed by exactly N bytes of a JSON-RPC 2.0 body (other headers may appear before the blank line; ignore all but `Content-Length`). Three body kinds:
- *Request*: `{jsonrpc, id, method, params}` — expects exactly one response with the same `id`. Both sides may send requests: the client (hover, completion…) **and the server** (`workspace/configuration`, `workspace/applyEdit`). Every received request must be answered — with a `MethodNotFound` error if unhandled. Ignoring a server request can hang the server.
- *Response*: `{jsonrpc, id, result}` or `{jsonrpc, id, error: {code, message}}`. Correlated to its request purely by `id` (HUME allocates monotonically increasing integers).
- *Notification*: `{jsonrpc, method, params}` — no id, no response, may be sent freely in both directions.

**Lifecycle.** `initialize` request (client capabilities, workspace root) → server replies with `ServerCapabilities` → client sends `initialized` notification. Everything else only after that. Shutdown: `shutdown` request, then `exit` notification, then reap the process. Capabilities gate features: e.g. no `completionProvider` in the reply → server can't complete; features must check (B3) instead of firing blind.

**Document sync.** The client owns document truth. `textDocument/didOpen` (full text + `languageId` + integer `version`) starts server-side tracking; every edit sends `textDocument/didChange` in the form the server's own `textDocumentSync` capability declared: ranged `TextDocumentContentChangeEvent`s for `INCREMENTAL`, one collapsed whole-document event per flush for `FULL` (a server declaring `FULL` ignores `range` entirely and treats each event's `text` as the whole new document — sending it a ranged event desyncs its copy from the very first edit), and nothing at all for `NONE` or an unadvertised capability; before the handshake completes, `FULL` is assumed so nothing queued while `Starting` is silently dropped. `didSave` / `didClose` bracket the rest. Versions must be strictly increasing — HUME uses the generation of the buffer text's `TextVersion`. A server response computed against version K is stale if the buffer has moved past K (C6 handles this). `languageId` is `LanguageRegistry::lsp_language_id_of`, not `name_of` — the language's configured or bundled `languageId` override, defaulting to the name (some of HUME's names diverge from the LSP spec's well-known ids — `tsx` needs `typescriptreact`).

**Positions.** A protocol `Position` is `{line, character}` where `character` counts *code units in the negotiated encoding* — UTF-16 by default, UTF-8 when both sides agree via `positionEncoding` (3.17). It is never a byte offset, never a grapheme count, and never a Rust `char` count. All conversions go through P4's helpers. A `Range` is half-open: `end` is exclusive.

**URIs.** Documents are identified by URI (`file:///path/with/%20escapes`). `Buffer.path` (canonical) is the SSOT for outgoing URIs; incoming URIs are canonicalized before buffer lookup (P5).

## Steel API index

Every Steel-visible surface the LSP platform introduces — the lookup table for what a plugin can call. Conventions: `pane` = an opaque pane value (a buffer paired with the pane it was invoked/observed through, or none) — `equal?` and hash-keying compare by the underlying (buffer, pane) pair (steel-core `Custom::equality_hint`/`try_as_dyn_hash`), so two wrappings of the same invocation compare/hash equal, but two different panes on the same buffer do not; `(buffer-key pane)` narrows to just the buffer half for per-buffer plugin state that must coalesce regardless of which pane produced it (a command's own pane and a hook's pane-less value for the same buffer, say) — `core:git-diff`'s and `core:buffer-words`' per-buffer hashes, and every `debounce-by #:key`, key by this rather than by `pane` itself. A builtin that only needs the buffer (most of the table below) ignores `pane`'s pane half entirely and works the same whether or not one is present; a builtin that needs the pane itself (selections, viewport, an async LSP response's anchored UI) raises rather than defaulting when `pane` carries none, is stale, or no longer shows its own buffer — never an implicit guess at which pane to use. A builtin declares which of these it needs as its pane argument's type in the `builtins!` table (`hume-scripting/src/builtins/args/pane.rs`), and a focus-bound one (a UI opener, `insert-key!`, `paste-text!`, `lsp-show-status!`) declares that its pane must also be the focused one. `(buffer-panes pane)` is the explicit alternative: every pane currently showing `pane`'s buffer, focused pane first, so `(car (buffer-panes pane))` picks one on purpose where a builtin's own contract does not. positions produced by HUME builtins (viewport/params helpers' inputs) are 0-based and **char-indexed** — raw wire positions appear only inside an undecoded LSP response (a `JsonHandle`), and only `goto-location!` (which accepts a raw `Location` handle), the response-shaped setters (e.g. `completion-emit!`), or the explicit `lsp-position->char-offset`/`lsp-range->char-range`/`lsp-label-offsets->text` converters may consume them — the decoration setters take char offsets, not wire positions, so a caller never needs to know which server's encoding a wire position came in; Steel never does encoding *arithmetic* itself — every wire↔offset conversion routes through one of these named builtins, never ad hoc code. Callbacks take `(err result)` — exactly one is non-`#f`. A char offset/`char-col` is an *addressing* unit, never shown to a user; the unit shown is a grapheme column everywhere except one documented exception in `lsp-locations->places` — see the "User-facing column unit" decision row above.

| `(lsp-label-offsets->text label offsets)` → the slice of `label` a `ParameterInformation.label` `(start end)` wire offset pair names. `offsets` is the raw two-element list off the wire — a `JsonHandle` tagged with its producing server's negotiated encoding (it's itself pulled out of the same response `label` came from, via `json-ref`), which is what these offsets are counted in; the only wire offsets that index a *server-authored string* rather than a document, so no rope or `pane` is involved at all. Errors if `offsets` isn't a handle from a server response (a `json-parse` result, a hand-built list) — no server to have negotiated an encoding with — signature help's offset-form parameter labels, which HUME asks for by declaring `labelOffsetSupport` | builtin |
| `(lsp-locations->places locs)` → one `(hash 'path p 'line l 'grapheme-col-or-wire c 'buffer b 'location loc)` per raw `Location`/`LocationLink` (a `JsonHandle` from a server response) in `locs`, in order and unmerged (`#f` for one with no place to jump to: a URI that is not a `file://` one, or a line past the content of the file's open buffer), `'location` being the entry itself for `goto-location!`, `'buffer` being a buffer-only pane for the open buffer the target is (`#f` when the file is not open), so a plugin never matches URIs to buffers itself, decoded via `hume_lsp::location::decode_location` (same decoder `goto-location!` uses) — the display counterpart to `goto-location!`'s wire-position jump. Each entry reads its own tagged producing-server encoding straight off its `JsonHandle` — errors (aborting the whole batch) on an untagged one, same as `goto-location!`'s wire shape. `col` is an exact grapheme column when the target has an open buffer, otherwise the location's own wire `character` verbatim — this builtin never reads a target file, so it cannot refine that last case; see the "User-facing column unit" decision row above for the reasoning and the resulting unit divergence. Path, line, and column come from one decode so a drawer row can't name one location and measure another; Scheme applies `path->display` to the path but never decodes a URI itself. A location that can't be decoded at all (missing `uri`/`range`) errors the whole call rather than degrading its own row — see the "Malformed-location vs no-place degrade" decision row above | builtin |
| `(lsp-locations->merged-places locs)` → `(hash 'places l 'skipped n)`: `l` is `lsp-locations->places` without the `#f` entries and with the first entry kept for each path, line and column, the places to show or jump to, since several servers answering one request often name the same place; `n` counts the `#f` entries left out, so a caller reports them without decoding the answer again. Decoding and errors are `lsp-locations->places`'s, with the error naming whichever builtin was called | builtin |
| `(viewport-range pane)` → `(hash 'start-line first-line 'end-line end-line)`, 0-based end-exclusive, shown in `pane`'s own pane (with wrapping on, `'end-line` may run past the bottom edge) — raises if `pane` carries none, is stale, or no longer shows its own buffer, rather than guessing one | builtin |
| `(after! ms thunk)` → timer; `(cancel-timer! timer)` | builtin |
| `(debounce ms proc)` → debounced proc, one shared pending timer across all calls | builtin (bootstrap wrapper over `after!`) |
| `(debounce-by ms proc)` → debounced proc keyed per `(car args)` — independent pending timer per key, so a call keyed `k2` never cancels a still-pending call keyed `k1` | builtin (bootstrap wrapper over `after!`) |
| `(set-inlay-hints! pane source hints)` — `hints`: `(hash 'char-offset 'text 'side)` entries, `'side` `'before`/`'after`, `'char-offset` a char offset (`lsp-position->char-offset` converts an LSP wire position first); the Steel decoration surface speaks editor-native units only | builtin |
| `(register-sign-source! pane source priority)` — declares `source` a gutter sign channel at `priority`, scoped to `pane`. A source's slot is its rank among every source registered *for that buffer*, by `(priority desc, source asc)` — a property of the source, fixed the moment it registers for `pane`, not of any one `set-signs!` call; a registered source reserves its slot in that buffer even where it has placed no signs, which is what keeps the gutter width stable there as signs come and go instead of shifting per frame. A buffer neither source ever registers for (no LSP server attached, no git tracking) never reserves either slot. Re-registering `source` for the same `pane` replaces its priority and re-sorts it (last wins, matching `register-lsp-server!`); there is no `unregister-sign-source!` — a source holds its slot in a buffer for that buffer's life, across `:e!` and a view's new text, cleared only when the buffer itself closes. `core:lsp` registers `"lsp-diagnostics"` at priority `10` before it places or clears diagnostic signs for a buffer, and `core:git-diff` registers `"git-diff"` at priority `0` before it renders signs for a buffer; registering again at the same priority changes nothing | builtin |
| `(set-signs! pane source signs)` — `signs`: `(hash 'line 'text 'scope)` entries, `line` converts to that line's line-start char offset (and remaps through edits) at the host boundary; `text` is rejected if it holds a control character (a gutter lane has no tab stops, and the writer would drop it while the lane still reserved its width). `source` must already be registered for `pane` via `register-sign-source!` — `Err`, naming the builtin, otherwise. Under `gutter-signs=always`/`auto` (no `:N`) the column auto-sizes to the number of sources registered for that buffer — a source ranked at or past `:N` (or past `SignColumnConfig::MAX_SLOTS`, 127, under auto-size) doesn't fit and gets no slot at all; `:N` pins the column's width instead. See `gutter-signs` in the user manual | builtin |
| `(set-virtual-lines! pane source lines)` — each entry a hashmap, `'line`/`'text` required, `'side` (`'before`/`'after`, default `'after`), `'scope`, `'segments` (list of `(hash 'start-char-col 'end-char-col 'scope)` char-column ranges in `text`) optional; segments flipped byte→char offsets at the host boundary, validated there (bounds, ordering, non-overlap) rather than trusted from Steel, an edge inside a character widening to the whole character | builtin |
| `(set-eol-text! pane source lines)` — each entry `(hash 'line 'text 'scope)`; `#:hide-on-insert-line` (default `#f`) flags the entries to be dropped on the primary cursor's line while its pane types in Insert mode; text spliced at end-of-line via a second, `Inline`-kind `DecorationSource` provider, same shape as the inlay hints above. Never diagnostics-specific — the diagnostics plugin is just its first client | builtin |
| `(set-extra-highlights! pane source spans)` — `spans`: `(hash 'start-char 'end-char 'scope)` char ranges, validated non-empty and in-bounds at the host boundary, an edge inside a character widening to the whole character | builtin |
| `(set-line-backgrounds! pane source lines)` — each entry `(hash 'line 'scope)`; tints a full line's background, e.g. `core:git-diff`'s changed-line signs | builtin |
| `(diagnostics-for-buffer pane #:severity floor #:range (hash 'start-char s 'end-char e))` — entries carry `'start-char`, `'end-char`, `'start-line`, `'end-line` (one past the last line the diagnostic touches) and `'server`, the publishing server; the `#:range` raises when it ends before it starts or past the end of the buffer | builtin |
| `(diagnostic-counts pane #:severity floor)` → `(hash 'error e 'warning w 'info i 'hint h)`, below-`floor` severities 0, `floor` defaulting to `lsp-diagnostics-min-severity` as `diagnostics-for-buffer`'s does | builtin |

| `(apply-workspace-edit! pane wsedit #:expect-generation gen)` — every position in `wsedit` is counted in its own tagged producing-server encoding, read straight off its `JsonHandle`; errors if `wsedit` isn't tagged. ## Testing playbook

Four tiers, cheapest first.

1. **`hume-lsp` unit tests** (`cargo test -p hume-lsp`): codec framing round-trips, URI round-trips, the ChangeSet→LSP-edit converter against a string-mirror oracle, request-id correlation, completion-item snippet-stripping and lenient `TextEdit` decoding. No editor, no process spawns.
2. **Editor integration with the inline double** (`cargo test -p hume-editor`): `InlineLspBackend` answers scripted `(method → response)` fixtures synchronously — the LSP analog of `InlineParseBackend`, and the workhorse for most editor-level LSP tests. Editor test helpers: `key()` / `key_enter()` (`editor/tests/mod.rs`); remember key sequences must match `keymap/defaults.rs` (e.g. goto-last-line is `ge`, not `G`). `CompletionItem`'s own strict/lenient item-parsing unit tests live alongside it (`hume-editor/src/editor/completion/item/`), outside this tier's inline-double machinery.
3. **Steel-level tests** (`hume-editor/tests/scripting.rs` pattern): eval plugin code against `SteelCtxTestHarness` (`hume-scripting/src/context.rs`) or a full editor with the double — scripted server responses in, editor state assertions out. This is how `core:lsp` features are tested.
4. **Manual smoke** (record what you did in the PR/commit message): `cargo run -p hume-editor -- src/main.rs` with an `init.scm` containing `(register-lsp-server! "rust-analyzer" #:command "rust-analyzer") (set-language-servers! "rust" '("rust-analyzer"))`; exercise the feature; check `:messages` for protocol errors.

Test-writing rules that bite here specifically:
- **Independent oracle**: the ChangeSet→LSP-edit converter's own test applies the emitted LSP events to a plain `String` mirror and compares with the post-edit rope — never re-derive expectations through the converter itself.
- **Flip check**: after writing a test, break the code (flip a condition) and confirm the test fails.
- **Grapheme rules don't apply to wire math**: protocol positions are char/code-unit based — use the position-encoding conversion helpers, not grapheme helpers, for codec/conversion code. Grapheme discipline still governs anything selection-like (e.g. "symbol under cursor"). Wire code stays plain `usize`/UTF-16 code units, never `CharOffset` — `hume_rope::offset::CharOffset` (see `CLAUDE.md`'s "Day-one architectural invariants") only wraps buffer char positions, so the type system itself keeps protocol math and buffer math from being mixed up.
- Shared-state test mutexes: recover from poison with `unwrap_or_else(|e| e.into_inner())`.

## Shipped scope

- **Prerequisites** — workspace groundwork with no LSP-visible behavior: serde/serde_json deps, batch position mapping, generalized event-loop wake, position encoding conversion, path↔URI, `ChangeSet` conversion, timer wheel.
- **LSP core (Rust data plane)** — the `hume-lsp` crate plus editor glue: spawn, handshake, document sync, diagnostics in memory. Crate scaffold, JSON-RPC codec, process management, `LspBackend` trait + inline double, lifecycle, request bookkeeping, document sync, server registration, diagnostics store, observability/lifecycle commands.
- **Steel platform** — the bridge and primitives that make Steel the feature layer: a plugin can reach any LSP method and any editor surface. JSON↔SteelVal codec, generic LSP bridge, introspection builtins, timers, decoration stores, edit/navigation primitives, hooks, completion orchestration, minibuffer prompt.
- **UI surfaces** — generic, Steel-scriptable widgets plus store-fed render wiring; LSP is their first client, not their owner. Diagnostic underlines, gutter signs, statusline element, popup, menu, drawer, completion menu, inline diagnostics, inlay hints.
- **Features (Steel, `core:lsp`)** — each feature is Steel code composing the platform and UI primitives above, tested against the inline double with scripted responses: hover, goto definition family, completions, diagnostics navigation, rename, references, signature help, formatting, code actions, inlay hints, document and workspace symbol pickers, `core:lsp` packaging + docs.
