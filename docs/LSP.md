Design and shared reference for HUME's Language Server Protocol support (shipped). All LSP decisions live here.

## Overview

**Goals**, in order:
1. **Community-extensible**: LSP features live in Steel so plugins can add features, server integrations, and custom UX without touching Rust.
2. **Snappy on big-realistic workloads**: rust-analyzer on a large crate, 100k-line files, 5k-diagnostic bursts, 1k-item completion lists, large terminals.

**Architecture: Steel on the control plane, Rust on the data plane.** The split is a *frequency cut*, not a per-feature assignment:

- Runs **per user intent** (a keypress-triggered command, a server response arriving, a menu selection) → Steel. A Steel dispatch costs tens of nanoseconds against a 16 ms frame budget (P8 measured ~76ns/call for a registered no-op builtin, 10k calls, release build — includes Steel loop overhead, so real dispatch is at or below that).
- Runs **per frame, per scroll row, or over unbounded collections** (rendering, diagnostic bursts, completion filtering, position math over edits) → Rust.

Two structural guardrails keep the experience snappy *by construction*, not by discipline:
- **Bulk data never crosses the Rust↔Steel boundary on recurring paths** (per-frame, per-keystroke, per-scroll). Diagnostics and completion items live in Rust-side stores; Steel sees signals, bounded subsets, and policy knobs. A one-time ingest at user-intent frequency (a completion response passing through Steel into the store) is the calibrated exception — confirmed to hold at 1k items (see the Bulk-data guardrail row below).
- **Steel never runs on the render path.** Steel writes data stores; Rust providers render from them every frame.

Rust therefore ships a *platform* — transport, document sync, stores, render providers, a generic LSP bridge, scriptable UI widgets — and the features themselves are Steel code in a `core:lsp` plugin: send request → transform response → call a UI/store builtin. A community plugin author writes the exact same three-line shape.

**v1 feature set**: diagnostics, completions, hover, go-to-definition (+ declaration / type-definition / implementation), rename, references, signature help, formatting, code actions, inlay hints.

**Non-goals for v1**: semantic tokens, snippet placeholder navigation, `workspace/symbol`, document symbols, code lens, DAP, multiple servers per language or buffer.

**Implementation shape** (five macro-steps):
1. **Step 0 — Prerequisites**: workspace groundwork (serde, position mapping, event-loop wake + timers, encodings, URIs, the boundary-cost spike).
2. **Step 1 — LSP core (Rust data plane)**: the `hume-lsp` crate (transport + client) and editor glue (document sync, diagnostics store, registration).
3. **Step 2 — Steel platform**: the generic bridge, codec, stores, edit/navigation primitives, and hooks that let Steel drive everything.
4. **Step 3 — UI surfaces**: scriptable widgets (popup, menu, drawer) and store-fed render wiring (underlines, signs, virtual lines).
5. **Step 4 — Features (Steel)**: the `core:lsp` plugin composing Steps 2–3 into user-facing features.

Steps 1–3 are ordered by dependency but Step 4 tasks unlock incrementally — each feature can land as soon as the primitives it composes exist.

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| LSP architecture | **Hybrid: Steel control plane, Rust data plane** | Rust owns transport, JSON-RPC, document sync, bulk stores, and rendering. Steel owns behavior: every user-facing feature is Steel code composing Rust primitives. The boundary is frequency: per-user-intent work may be Steel; per-frame / per-scroll / unbounded-collection work must be Rust. Maximizes community extensibility without sacrificing latency. |
| Feature delivery | **Generic LSP bridge + `core:lsp` plugin, not hardcoded Rust features** | `(lsp-request server method params callback)` / `(lsp-notify …)` / `(on-lsp-notification method handler)` make any protocol method reachable from Steel. v1 features ship as the `core:lsp` plugin using the same public surface plugins get — dogfooding guarantees the bridge is complete. Rust volume is similar to hardcoding v1 (generic infra costs more up front), but marginal feature cost afterward is a Steel file anyone can write. |
| Bulk-data guardrail | **Bulk never crosses the boundary on recurring paths** | Diagnostics are ingested, stored, and remapped in Rust; Steel receives change *signals* and pulls bounded subsets (visible lines, top-N). Completion items live in a Rust store with a Rust per-keystroke filter; Steel orchestrates and sees the top-N. The one crossing allowed is a per-user-intent ingest (a completion response flowing through the B2 callback into `completion-begin!`), measured at 1k items: ~0.75–0.8ms JSON→SteelVal conversion + ~0.26ms for one Steel-side pass over the converted list ≈ 1ms total, well under the 2ms threshold. `lsp-request` does not need a raw-response-routing escape hatch. |
| Render decoupling | **Data-driven decoration stores; Steel never on the render path** | Steel setters (`set-inlay-hints!`, `set-signs!`, `set-virtual-lines!`, …) write Rust-side stores; the engine's `DecorationSource` trait (unifying the former `HighlightSource`/`VirtualLineSource`/`InlineDecoration`, plus `SignSource` separately) renders from them each frame with zero Steel involvement. |
| UI widgets | **Rust-rendered, Steel-fed** | Cursor popup, selection menu, drawer list are generic Rust widgets taking content + callbacks from Steel (`show-popup!`, `show-menu!`, `show-drawer-list!`). LSP is their first client, not their owner — any plugin can use them. |
| Symbol rename | **LSP-only in v1** | `textDocument/rename` via `core:lsp`; an unattached buffer reports unsupported through the capability guard. A tree-sitter local-rename fallback (file-local, via `locals.scm`) is out of core:lsp's scope — a separate feature to design later, not part of this plugin. |
| Position remapping through edits | **Batch `PosMapCursor`, never per-position** | Diagnostic ranges, bookmarks, and any stored positions must be remapped through edits with the batch primitive: `ChangeSet`'s public `PosMapCursor` (`hume-editing/src/changeset/mod.rs`) maps sorted position lists through one cursor. Per-position one-shot mapping is O(positions × ops). |
| Protocol types | **`lsp-types` crate** | De-facto standard (Helix, rust-analyzer ecosystem), spec-tracking, serde-based. Hand-transcribing the LSP spec is weeks of error-prone tedium. |
| Transport concurrency | **std threads + mpsc; `LspBackend` trait mirroring `ParseBackend`** | Per server: reader thread (blocks on server stdout), writer thread (stdin), stderr logger. Messages cross to the main loop via mpsc; `prepare_frame` drains; the reader/stderr threads wake the main loop directly via a cross-thread `WakeCallback` after posting — byte-for-byte the `ThreadedParseBackend` pattern. No tokio: transport concurrency is never the bottleneck (heavy JSON parse lands on reader threads off the main loop; incremental `didChange` is proportional to the edit, not the file), and a runtime would split a fully-sync codebase into two concurrency idioms. The trait boundary is the insurance policy. Cost accepted: request timeouts are hand-rolled (deadline check at drain time). |
| Crate boundary | **New `hume-lsp/` crate** | Follows the `hume-treesitter` precedent (zero `Editor` dependency, acyclic). Full rationale: `hume-lsp/src/lib.rs`'s module doc. |
| Server instance scope | **One per (language, workspace root)** | First buffer open whose (language, resolved root) pair has no running server spawns it (C3 + C5 handshake); later buffers with the same pair attach. Correct `rootUri` when two projects share a session; the diagnostics store already keys by server. |
| Position encoding | **Negotiate `utf-8`, fall back to UTF-16 conversion** | LSP defaults to UTF-16 code-unit columns; 3.17's `positionEncoding` capability lets client and server agree on `utf-8`. HUME is char/grapheme-based, so both paths need conversion helpers; ropey 1.6 provides `char ↔ utf16_cu` primitives (`char_to_utf16_cu` / `utf16_cu_to_char`, unconditional — no feature flag in 1.x) for the fallback. Never assume byte == column. |
| Timers | **Timer wheel in the event loop; `(after ms thunk)` + debounced hooks in Steel** | The loop already degrades to `poll(timeout)` when async work is pending; a nearest-deadline timer wheel bounds that timeout naturally. Required for debounced inlay-hint refresh, signature-help triggering, and completion debounce — without it, scroll- and keystroke-driven Steel work would fire unthrottled. |
| Server→client requests | **Answered in Rust, never surfaced to Steel in v1** | JSON-RPC requires a response to every request, including server-initiated ones. C6 dispatches them: `workspace/configuration` answered from C8 settings, `workspace/applyEdit` applied via the B6 engine, `client/registerCapability` / `window/workDoneProgress/create` acknowledged and ignored, anything else gets a `MethodNotFound` error response. Steel handles notifications only (`on-lsp-notification`) — response obligations stay where timeouts can't be caused by a plugin. |
| Diagnostics exposure granularity | **`diagnostics-for-buffer` caps at 1 000 items** | Measured JSON→SteelVal conversion (steel-core's built-in `IntoSteelVal for serde_json::Value`) at 100/1k/5k diagnostic-shaped items, release build: ~86µs / ~750µs / ~4.2ms. Confirms the hub's 1 000 default with comfortable margin — even the uncapped 5k case stays under 5ms for a per-user-intent pull (not a per-frame path). Filtered by the optional `#:severity` / `#:range` arguments before the cap applies. |
| Steel completion scorer budget | **Re-rank Rust's top-N only (N = 64)** | This is architectural, not just a speed call: per-item conversion/iteration cost is low (~0.8–1µs/item) but completion filtering runs *per keystroke* — the hub's frequency-cut rule (recurring paths must be Rust, regardless of measured Steel throughput) means an unbounded Steel scorer would violate the guardrail even though it would be numerically affordable at 1k items. Bounded top-64 re-rank confirmed as the default. |
| LSP idle wake | **Cross-thread waker, no poll cadence** | The LSP transport threads signal the main loop's wait primitive directly after posting a result, so `LspState::next_wake` reports real deadlines only (the earliest pending-request deadline, plus the statusline spinner's cadence while Starting/`$/progress`). |
| WorkspaceEdit on unopened files | **Open-as-buffer** | Rename/code actions can touch files with no open buffer. Chose open-as-buffer (undoable, dirty, user saves via `:wa`) over a direct fs write (atomic but bypasses undo) — consistent with every other HUME mutation going through the undo tree. `apply_workspace_edit` validates every file first (opening unopened ones along the way) and only commits once all have passed, then reports `"N buffers modified — :wa writes all"` to the message log. |
| `set-extra-highlights!` tier | **New variant `Extra` between `Syntax` and `SearchMatch`** | Plugin spans beat syntax, lose to search/diagnostics/brackets. See `HighlightTier`'s doc comment in `hume-engine/src/providers.rs` and `TIER_COUNT` in `hume-engine/src/style/highlight.rs`. |
| `$/progress` | **Message-log only in v1** | No spinner element added — the statusline's only new element is `Diagnostics` (error/warning counts). `$/progress` routes to the message log via the existing server-notification handling; a spinner element is Future. |
| Hover surface (revised) | **Popup only — cursor or docked layout, never the drawer** | `show-popup!`'s ⅓-pane-height max is the threshold for the cursor layout. Content taller than that docks instead (`#:anchor 'bottom`): a full-width band above the statusline that reserves pane space like the drawer, but keeps popup semantics (plain scroll, no selection) — hover overflow is not a pick-list, so it never uses `show-drawer-list!` (which stays references/goto/diagnostics-only). Rust never chooses between the two layouts — it's a Steel-side branch on formatted content length, same as before. |
| `register-trigger-chars!` context | **Relaxed to any context, no init/plugin-load gate** | Servers register their trigger characters from inside their `on-lsp-attach` handler, which runs as plain command context — the previous init-only gate made this uncallable. No feature needs init-time registration, so the gate was dropped entirely rather than widened to "init or command." |
| Per-range formatting fan-out join | **Hand-rolled in Steel (`lsp/format-fan-out!`), not a Rust primitive** | The `rangeFormatting`-per-range fallback joins N in-flight requests with a `pending` counter, an `edits` accumulator, and an `aborted` flag, all in `format.scm`. Right altitude for its one caller — `Effect::LspRequest` is strictly one-request/one-callback, so there's no existing request-group primitive this is standing in for. Promotion trigger, not a one-off exemption: a second caller needing the same join is the point to start looking for a shared shape; a third makes it mandatory, as a Rust request-group primitive in `hume-editor/src/editor/lsp/bridge.rs` — the join itself (dispatch, counting, abort) is bridge-side work Scheme only requests, not a `lib.scm` helper. |
| Steel settings read access | **New `(get-option [bid] key)` builtin, symmetric with `set-option!`** | Multiple features need to read a setting from Steel (e.g. `tab-width`/`tab-style` → `FormattingOptions`); no getter existed. Resolves buffer overrides against the *passed* `bid`, falling back to the focused buffer only when `bid` is omitted; `Err` on an unknown key. `hume-editor/src/settings.rs`'s `setting_value` covers every `global`/`buffer`/`subfield` macro-declared key, plus the hand-written `manual_keys` entries (`statusline`) — `whitespace-*` round-trips through its own generated `subfield` arm, not through `manual_keys`. Required adding `Display` impls to `LineNumberStyle` and `WrapMode` (mirroring `TabStyle`'s existing `FromStr`+`Display` pair) so every `from_str`-parsed setting type can round-trip through the same generic accessor. |
| Completion accept/refilter Steel visibility | **`on-completion-accept` + `on-completion-refilter` hooks; `StoredCompletionItem` retains the raw response item** | `on-completion-accept (bid item)` fires after the *whole* accept (main edit + any `additionalTextEdits` + a `completionItem/resolve` round trip, all atomic — see the row below) lands, `item` the accepted item's full raw JSON; a plain extension point now, not Steel's job to apply anything further. `on-completion-refilter (bid filter-text)` fires from the per-keystroke refilter path but **only while the session's `isIncomplete` flag is set** — bounded to the one case that needs it, not an unconditional per-keystroke hook (which the hub's frequency-cut rule would forbid). |
| `additionalTextEdits`/`completionItem/resolve` ownership | **Rust owns the accept, atomically** | `CompletionSession::accept` (`hume-editor/src/editor/lsp/completion/`) batches the main edit and any `additionalTextEdits` into one `apply_text_edits_returning_cs` call — all wire positions computed by the server against the *same* pre-accept document, so no relative adjustment between them is needed. When the item lacks `additionalTextEdits` entirely (not just an empty array) and the server advertises `resolveProvider`, accept sends `completionItem/resolve` synchronously (through the ordinary `LspCallback`/`stale_check` machinery every `lsp-request` uses, so `:lsp-stop`'s `drain_pending` teardown sweeps it for free). The response's positions are decoded against the pre-accept rope, then mapped *forward* through the accept edit's own `ChangeSet` (`ChangeSet::map_ranges`) onto the buffer as it now stands. |
| `lsp.inlay-hints` default | **`false` — opt-in** | Off-by-default. |
| `workspace.workspaceEdit` client capability | **Declared: `documentChanges`, `resourceOperations` (create/rename/delete), `failureHandling: Abort`** | Without this declaration servers refuse `textDocument/rename` outright. See `resource_operations` in `hume-lsp/src/client.rs` for why it must stay non-empty specifically. |
| Wire codec null-result handling | **`hume-lsp/src/codec.rs`'s `result`/`error` distinguish "field absent" from "field present as JSON `null`"** | A spec-valid `{"id":N,"result":null}` response must not crash the connection. Full rationale: `codec.rs`'s doc comment on the field. |
| `map_ranges` on nested/overlapping ranges | **`hume-editing/src/changeset/mod.rs`: ends walked via an index permutation sorted by end value, not input order** | `ChangeSet::map_ranges` asserts its input sorted by *start*, but ends aren't necessarily non-decreasing in that same order for *nested* ranges (e.g. two LSP diagnostics on the same span). Full rationale: `map_ranges`'s own doc comment. |
| `textDocument.codeAction` client capability | **Declared: `codeActionLiteralSupport` (quickfix/refactor/source kinds), `isPreferredSupport`, `disabledSupport`** | A server withholds diagnostic-derived quickfixes entirely without this. See `code_action_literal_support` in `hume-lsp/src/client.rs` — found via manual smoke testing against rust-analyzer. |
| `diagnostics-for-buffer`'s `raw` field | **Each entry carries the original wire `Diagnostic` JSON verbatim** | `textDocument/codeAction`'s `context.diagnostics` must echo back the *raw* diagnostics currently shown in the request range — servers gate diagnostic-derived quickfixes on this, treating an empty array as "the client isn't showing any diagnostics here." `StoredDiag`'s `raw: serde_json::Value` field is captured at ingest before the wire `Diagnostic` is consumed, exposed as a `"raw"` key in `diagnostics-for-buffer`'s output; `actions.scm` extracts it directly, no position math in Steel. |
| Snippet completions | **Strip to plain text, Rust-side** | `insertTextFormat == 2` items get `${n:default}` rewritten to `default` and bare `$n` dropped at store ingress (see `strip_snippet` in `hume-editor/src/editor/lsp/completion/`) — no choices, no nested placeholders, no `\$` escapes. `raw` keeps the pristine snippet text for `completionItem/resolve`. Full snippet support (tabstop navigation) stays Future. |
| Multi-character inline inserts | **`hume-engine/src/format.rs`: one `Grapheme`/`Cell` per grapheme cluster of the insert text, not one cell for the whole string** | The frame holds one cell per terminal column; text wider than one cell must be split into one `Cell` per grapheme or its spillover gets overwritten. Full rationale: `format.rs`'s doc comment at the push site. |
| Server crash policy | **Manual `:lsp-restart [language]` only — no auto-restart** | `core:lsp` Steel command over an `lsp-restart!` builtin (queued onto `PendingLspServerOp`, applied by `Editor::apply_lsp_server_op`) — see the "LSP server lifecycle ownership" row above. Stops then respawns through the same spawn path. |
| `workspace/configuration` flow | **`register-lsp-server!`'s `#:settings` blob pushed once as `didChangeConfiguration` after `initialized`, and resolved per-item (dotted `section` walked into the blob — VS Code semantics: no section returns the whole blob, a miss returns `null`) to answer `workspace/configuration` pull requests** | Resolution and push live in `hume-lsp/src/client.rs` (`resolve_config_section`, `workspace_configuration_response`); the editor glue resolves the requesting server's own config in `hume-editor/src/editor/lsp/mod.rs`'s `ServerRequest` dispatch arm. A miss is expected and harmless, same as in Helix; see `docs/LSP-INSTALL.md`'s "Config delivery & per-server audit" section for the per-server audit. |
| Multiple servers per language | **Last-wins: a second `register-lsp-server!` for a language *replaces* its config (matching `define-language!`), rather than being rejected.** Running clients on the old config are left untouched until their next spawn — a caller needing an immediate respawn unregisters explicitly first via `unregister-lsp-server!`. Both builtins are queued and applied via `Editor::apply_lsp_server_op` at the end of an init eval or a command/hook body — see `docs/LSP-INSTALL.md`'s "Registration model" section. A *lazy* plugin activation (`#:languages`/`#:events`/`#:commands`) applies its own queued registration synchronously too, so the buffer that triggered activation attaches in that same call. | Full rationale (why last-wins beats a hard error, why the replacement logs at `Severity::Trace`): `hume-editor/src/editor/lsp/registry.rs`'s `apply_pending_lsp_server_reg` doc comment. |
| `(declared-plugins)` scope | **Reports every declared plugin, `core:*` included** | Generic introspection, not scoped to any one consumer. `plum/missing-plugins` (`plugins.scm`) is where the never-install-core filter belongs — core plugins being un-installable is PLUM's install-list policy, not a property of what `init.scm` declared, so it filters `core:*` back out locally rather than the builtin doing it globally. |
| Supersede-cancel for `lsp-request` | **Explicit opt-in `#:supersede <key>` on `lsp-request`** | A new request with `#:supersede "k"` cancels the caller's own previous still-pending request filed under `(server, "k")` (mechanism: `hume-scripting/src/builtins/{mod,lsp}.rs`, `runtime/plugins/core/lsp/completion.scm`). **Never automatic by method name** — that would silently cancel two features' concurrent same-method requests (e.g. two plugins both calling `textDocument/hover`) that were never meant to race each other; explicit opt-in keeps the policy in Steel, where it belongs. |
| LSP server lifecycle ownership | **`core:lsp` owns install, uninstall, registration, and runtime management (`:lsp-status`/`:lsp-stop`/`:lsp-restart`) end to end; `core:plum` is not involved** | A package manager alone must not silently turn on diagnostics with no way to interact with them. See `runtime/plugins/core/lsp/README.md`'s "Runtime management" section and `docs/LSP-INSTALL.md`'s "Placement" and "Registration model" sections. |
| `steel-language-server`'s host-globals reach | **A shipped, generated file + `register-lsp-server!`'s `#:env`, not a runtime write** | `steel-language-server` (registered by `core:steel-server`) learns HUME's own Steel identifiers only by finding a `(#%register-global "name")` file in the directory named by `$STEEL_LSP_HOME` at its own startup — no CLI args, no `initializationOptions` channel exists for this. `runtime/plugins/core/steel-server/lsp-home/hume-globals.scm` is generated from `ScriptingHost::host_global_names` (diffed against a pristine engine to drop upstream Steel stdlib names, then filtered against `is_internal_name` — `%`-prefixed private primitives, `*earmuffed*` internal state, `hm.`-prefixed `steel/meta` aliases, `#`-prefixed steel-core internals — so the file only lists names a plugin author could actually type) and checked in; `hume-editor`'s `hume_globals_scm_matches_generated_host_names` test fails the build if it drifts. The plugin points `#:env '(("STEEL_LSP_HOME" . dir))` at that directory, gated on `hume-globals.scm` itself existing inside it (not just the directory) — the server's `read_dir` on a missing `$STEEL_LSP_HOME` panics at startup with no fallback, so the existence check is load-bearing. |
| LSP default keybindings | **All bound by `core:lsp` itself (`bind-key!` in `plugin.scm`), none in Rust's native default keymaps** | With no `core:lsp` loaded or declared, none of its keys exist at all — no post-init keymap lint warning, no dead binding. See `runtime/plugins/core/lsp/README.md`. |
| `lsp.rs` module split + embedded Scheme as `.scm` | **`builtins/lsp.rs` holds server lifecycle, request/notify bridge, and introspection only. Decorations/diagnostics live in `decorations.rs`; completion orchestration + `register-trigger-chars!` in `completion.rs`; text-edit/goto-location primitives in `edits.rs`; generic buffer/cursor reads (`viewport-range`, `selections-linewise?`, `symbol-under-cursor`) in `buffers.rs`; `%prompt!` in `ui.rs`. `BOOTSTRAP` and `PRINT_GATE_SHIMS` live as `builtins/bootstrap.scm`/`builtins/print_gate_shims.scm`, embedded via `include_str!`.** | Every builtin module stays scoped to one concern; every Steel name, gate kind, and behavior is unchanged from a plugin author's perspective. |
| Virtual-line-aware scroll/cursor math | **Landed end to end, both wrap modes** | `hume-engine/src/rows.rs`'s `RowMap` owns the display-row list, and every consumer reads it: `cursor::content_pos`/`screen_to_char_offset`, `scroll::ensure_cursor_visible`/`scroll_cursor_to_row`/`clamp_viewport_top`, `mouse.rs`'s wheel scroll, `visual_move::move_vertical`, and `pane_render::render_pane` itself. There is no wrap-mode split to caveat — a line occupies one content row with wrapping off and N with it on, which is the only difference the map sees. Inline decorations count toward the same rows, so an inlay hint that wraps a line moves the rows below it for scroll math exactly as on screen. |
| Wire `languageId` vs HUME's language name | **Per-language override (`LanguageIdentity.lsp_language_id`, set via `define-language!`'s `#:language-id` keyword), defaulting to the name** | HUME's language names mirror Helix's `languages.toml`, which diverge from the LSP spec's well-known document identifiers for a handful of languages (`tsx` needs `typescriptreact`, `jsx` needs `javascriptreact`, etc.) — sending the bare name made validating servers (e.g. `typescript-language-server`) log an "Invalid languageId" warning and silently correct it. `scripts/sync-grammars.py` carries Helix's own `language-id` key through into the bundled `languages.scm`; `lsp_did_open` (`sync.rs`) reads `LanguageRegistry::lsp_language_id_of`, never `name_of`. `define-language!` converted from a `syntax-rules` macro to a plain function to take the optional trailing keyword — verified to keep working unqualified inside `(require)`d plugin modules the same way `register-lsp-server!` (a keyword-arg function in `bootstrap.scm`) already does. |
| User-facing column unit | **Grapheme column everywhere a buffer is open; the location's own wire unit otherwise, as a documented exception** | The 2026-08-22 column-naming sweep made every internal identifier kind-explicit but left the *displayed* value alone; `:diagnostics` rendered a char column, the goto/references drawer rendered a raw wire `character` (UTF-16 code units), and the statusline a grapheme column — three different numbers for one cursor position on any non-ASCII line. Grapheme column wins because it's already what the statusline shows and what the editing model itself counts in (`grapheme_col_in_line`'s doc: "matches how many times the user pressed →"). `diagnostics-for-buffer` now returns both `char-col` (addressing, feeds `goto-location!` unchanged) and `grapheme-col` (display, new). The goto/references drawer initially resolved an unopened target's column the same way, reading its file from disk once per distinct path — synchronous, uncapped, on the frame loop, to refine one number for a row the user might never select. That was rejected as disproportionate: `(lsp-locations->display-parts locs)` (`hume-editor/src/editor/lsp/introspect.rs`'s `location_display_parts`) now reads no file at all — an open buffer still gets an exact grapheme column, but an unopened target's row shows the location's own wire `character` verbatim, diverging from the true grapheme column only when non-ASCII text precedes it on the same line. This is the one sanctioned exception to "wire `character` and `char-col` are never rendered directly"; it is not open to reuse elsewhere. |
| Malformed-location vs out-of-range degrade | **A row exists only if it can be selected: abort the whole `lsp-locations->display-parts` batch on a location missing `uri`/`range`; degrade only the one row for an open buffer whose line is out of range** | The drawer's `on-select` *is* `goto-location!` — a location missing `uri` or `range.start` names no destination, so a row for it would be clickable and lead nowhere. An open buffer whose reported line doesn't exist is different in kind: the destination is real and the jump still works, only the grapheme column can't be counted (an *unopened* target never triggers this — it always gets a column, per the row above). Both `goto-location!` and `lsp-locations->display-parts` decode a location through the one shared `hume_lsp::location::decode_location` (`hume-lsp/src/location.rs`), so a location valid enough to display a row for is exactly one valid enough to jump to. A non-`file:` URI (a server HUME can't open, e.g. jdtls's `jdt://`) follows the same abort rule; the error names the URI and the unsupported scheme rather than showing `NotFileScheme`'s `Debug` form. |

## LSP protocol primer

Compact model of the protocol as HUME uses it. Full spec: <https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/>. The `lsp-types` crate mirrors the spec's type names — when this doc names a protocol type, that's the `lsp_types::` type.

**Wire format.** Each message is `Content-Length: N\r\n\r\n` followed by exactly N bytes of a JSON-RPC 2.0 body (other headers may appear before the blank line; ignore all but `Content-Length`). Three body kinds:
- *Request*: `{jsonrpc, id, method, params}` — expects exactly one response with the same `id`. Both sides may send requests: the client (hover, completion…) **and the server** (`workspace/configuration`, `workspace/applyEdit`). Every received request must be answered — with a `MethodNotFound` error if unhandled. Ignoring a server request can hang the server.
- *Response*: `{jsonrpc, id, result}` or `{jsonrpc, id, error: {code, message}}`. Correlated to its request purely by `id` (HUME allocates monotonically increasing integers).
- *Notification*: `{jsonrpc, method, params}` — no id, no response, may be sent freely in both directions.

**Lifecycle.** `initialize` request (client capabilities, workspace root) → server replies with `ServerCapabilities` → client sends `initialized` notification. Everything else only after that. Shutdown: `shutdown` request, then `exit` notification, then reap the process. Capabilities gate features: e.g. no `completionProvider` in the reply → server can't complete; features must check (B3) instead of firing blind.

**Document sync.** The client owns document truth. `textDocument/didOpen` (full text + `languageId` + integer `version`) starts server-side tracking; every edit sends `textDocument/didChange` in the form the server's own `textDocumentSync` capability declared: ranged `TextDocumentContentChangeEvent`s for `INCREMENTAL`, one collapsed whole-document event per flush for `FULL` (a server declaring `FULL` ignores `range` entirely and treats each event's `text` as the whole new document — sending it a ranged event desyncs its copy from the very first edit), and nothing at all for `NONE` or an unadvertised capability; before the handshake completes, `FULL` is assumed so nothing queued while `Starting` is silently dropped. `didSave` / `didClose` bracket the rest. Versions must be strictly increasing — HUME uses the buffer's `text_gen`. A server response computed against version K is stale if the buffer has moved past K (C6 handles this). `languageId` is `LanguageRegistry::lsp_language_id_of`, not `name_of` — the language's registered `#:language-id` override, defaulting to the name (some of HUME's names, mirrored from Helix, diverge from the LSP spec's well-known ids — `tsx` needs `typescriptreact`).

**Positions.** A protocol `Position` is `{line, character}` where `character` counts *code units in the negotiated encoding* — UTF-16 by default, UTF-8 when both sides agree via `positionEncoding` (3.17). It is never a byte offset, never a grapheme count, and never a Rust `char` count. All conversions go through P4's helpers. A `Range` is half-open: `end` is exclusive.

**URIs.** Documents are identified by URI (`file:///path/with/%20escapes`). `Buffer.path` (canonical) is the SSOT for outgoing URIs; incoming URIs are canonicalized before buffer lookup (P5).

## Steel API index

Every Steel-visible surface the LSP platform introduces — the lookup table for what a plugin can call. Conventions: `bid` = buffer id value — `equal?` and hash-keying compare by the underlying id (steel-core `Custom::equality_hint`/`try_as_dyn_hash`), so plugin code may use ordinary `equal?` and hash-keyed per-buffer state directly; positions produced by HUME builtins (viewport/params helpers' inputs) are 0-based and **char-indexed** — raw wire positions appear only inside undecoded LSP response hashmaps, and only `goto-location!` (which accepts a raw `Location` hashmap), the response-shaped setters (e.g. `completion-begin!`), or the explicit `lsp-position->offset`/`lsp-range->offsets`/`lsp-label-offsets->text` converters may consume them — the decoration setters take char offsets, not wire positions, so a caller never needs to know which server's encoding a wire position came in; Steel never does encoding *arithmetic* itself — every wire↔offset conversion routes through one of these named builtins, never ad hoc code. Callbacks take `(err result)` — exactly one is non-`#f`. A char offset/`char-col` is an *addressing* unit, never shown to a user; the unit shown is a grapheme column everywhere except one documented exception in `lsp-locations->display-parts` — see the "User-facing column unit" decision row above.

## Testing playbook

Four tiers, cheapest first.

1. **`hume-lsp` unit tests** (`cargo test -p hume-lsp`): codec framing round-trips, URI round-trips, the ChangeSet→LSP-edit converter against a string-mirror oracle, request-id correlation. No editor, no process spawns.
2. **Editor integration with the inline double** (`cargo test -p hume-editor`): `InlineLspBackend` answers scripted `(method → response)` fixtures synchronously — the LSP analog of `InlineParseBackend`, and the workhorse for most editor-level LSP tests. Editor test helpers: `key()` / `key_enter()` (`editor/tests/mod.rs`); remember key sequences must match `keymap/defaults.rs` (e.g. goto-last-line is `ge`, not `G`).
3. **Steel-level tests** (`hume-editor/tests/scripting.rs` pattern): eval plugin code against `SteelCtxTestHarness` (`hume-scripting/src/context.rs`) or a full editor with the double — scripted server responses in, editor state assertions out. This is how `core:lsp` features are tested.
4. **Manual smoke** (record what you did in the PR/commit message): `cargo run -- src/main.rs` with an `init.scm` containing `(register-lsp-server! "rust" #:command "rust-analyzer" #:root-markers '("Cargo.toml"))`; exercise the feature; check `:messages` for protocol errors.

Test-writing rules that bite here specifically:
- **Independent oracle**: the ChangeSet→LSP-edit converter's own test applies the emitted LSP events to a plain `String` mirror and compares with the post-edit rope — never re-derive expectations through the converter itself.
- **Flip check**: after writing a test, break the code (flip a condition) and confirm the test fails.
- **Grapheme rules don't apply to wire math**: protocol positions are char/code-unit based — use the position-encoding conversion helpers, not grapheme helpers, for codec/conversion code. Grapheme discipline still governs anything selection-like (e.g. "symbol under cursor"). The `no_raw_char_stepping_in_motion_code` lint only scans `ops/` + `lines.rs`/`word.rs` (plus `hume-rope`'s own `lines.rs`); don't move protocol math there.
- Shared-state test mutexes: recover from poison with `unwrap_or_else(|e| e.into_inner())`.

## Deferred / Future

- **Semantic tokens** — delta decode (integer-array crunching) in Rust feeding a highlight store; orchestration Steel. Interacts with tree-sitter highlight priority.
- **Snippet placeholder navigation** — parsing maybe Steel; insert-mode tabstop state machine with multi-cursor selections likely Rust (see open question).
- **`workspace/symbol` + document symbols** — plugin-writable via B2 + drawer, or via the `core:pickers` fuzzy finder now that it's shipped; no symbols picker built yet.
- **Code lens** — plugin-writable via B2 + B5 stores + `workspace/executeCommand`.
- **Multiple servers per language / per buffer** — Rust routing + result merging. `LspState.servers: HashMap<ServerId, ServerEntry>` is process-identity-keyed, not language-keyed. What *is* language-keyed today: `LspState.configs: HashMap<LanguageName, LspServerConfig>` (one registration per language — a second `register-lsp-server!` for the same language replaces it, see the row above) and each running `ServerEntry.language: Option<LanguageName>` (one language per server). Two languages registered under the same `command` already spawn two independent processes (`lsp_attach_buffer`'s `(language, root)` match never reuses a running entry across languages), so per-server tracking doesn't assume one process per command. The concrete gap for real multi-server-per-language support: registration identity is language, 1:1 with a config and a running server; landing this needs (a) a registration identity distinct from language (a name, with a language list), (b) `ServerEntry.language` → a registration name + a `LanguageName -> [registration name]` map, (c) `resolve_server`/`lsp_targets` (`hume-editor/src/editor/lsp/introspect.rs`, `registry.rs`) accepting a registration name in addition to a language, (d) the Steel API staying language-keyed and returning singleton lists until a caller needs otherwise. `LanguageName` (`registry.rs`) is a plain `String` alias marking every language-keyed signature in `registry.rs`/`introspect.rs`/`mod.rs` today.
- **Bounded auto-restart** for crashed servers (policy knob Steel-side).
- **`workspace/didChangeWatchedFiles`** via a real file watcher (existing ROADMAP Future item) — not implemented in v1; the capability is not advertised.
- **DAP** — entirely separate protocol; out of scope, noted only as the same platform pattern (Rust transport, Steel behavior) applied again.
