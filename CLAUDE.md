# HUME — Project Instructions

## What is this?
HUME (HUME's Unfinished Modal Editor) is a modal text editor for the terminal, written in Rust. This is an agentic programming / learning project.

## Key files
- `README.md` — Project description
- `docs/CRATES.md` — Workspace crates, what each owns, dependency edges
- `docs/ROADMAP.md` — Open questions and milestones
- `docs/LSP.md` — LSP design, architecture, and decisions
- `docs/LEARNING.md` — Concepts and Rust patterns explained as they arise

## Architectural invariants (quick orientation)
- **Named commands** (`hume-ops/src/edit/`, `hume-ops/src/motion/`) are pure functions of buffer + selections (plus command-specific params like `count: usize`, `MotionMode`). Edits also return a `ChangeSet`. They have no knowledge of keys — `hume-ops` doesn't depend on `hume-editor`, so this is compiler-enforced, not just discipline.
- **Keymaps** (`hume-editor/src/editor/keymap/`) map `KeyEvent` sequences to command names via a trie. Per-mode keymaps (Normal, Extend, Insert).
- **Buffer invariant**: every buffer always ends with a structural `\n`. Cursors always satisfy `head < len_chars()`.

## Rules
- **Record the *why* of a decision in a source comment** at the implementing site, not in ROADMAP — comments stay next to the code they explain instead of drifting into a second, unmaintained copy of it. Update `docs/ROADMAP.md` only to remove a resolved open question or when milestones change.
- **Rust idioms**: Write idiomatic Rust. Prefer pattern matching, iterators, and the type system over runtime checks. Use `Result` and `Option` — no `.unwrap()` in non-test code.
- **Terminal compatibility**: Require true color (24-bit) and synchronized output. Prefer kitty keyboard protocol but fall back gracefully to legacy encoding when unavailable. No shims for truly ancient terminals.
- **Cross-platform**: macOS primary, Linux and Windows (Git Bash / WSL) secondary. Use `termina` or similar abstractions for platform differences — no platform-specific code unless behind `cfg` gates.
- **Keep it simple**: This is a learning project. Prefer clarity over cleverness, and direct solutions over premature abstraction.
- **Testing**: Every editing command, text object, and selection operation must be tested. No untested commands. Core editing logic uses state triples (`initial, op, expected` with cursor/selection markers). Appearance (glyphs, spacing, exact rendered strings) is tested with `insta` snapshots — inline for short one-line element strings, file snapshots for full-frame renders — never with hardcoded string assertions in unit tests; unit/integration tests assert data/semantics only. Verification sequence: `cargo fmt`, then run this exact command line from the repo root, exactly once, before pushing:
```
scripts/test-all.sh
```
`test-all.sh` matches CI exactly: it fetches the grammar fixtures the suite requires and runs doctests, so it supersedes a bare `cargo test` — never run a full `cargo test` before it, and never rerun the full suite after `fmt` (whitespace-only, doesn't invalidate a green run). **A second full run is forbidden** — this includes re-invoking `scripts/test-all.sh` piped through `tail`/`grep`/`tee` or any other filter "to double-check" a result already reported; that still executes the whole suite again. If the first run's outcome is unclear (truncated output, ambiguous exit), treat it as a successful run — do not re-run to settle the doubt. Narrow `cargo test <filter>` runs while iterating on a specific failure are fine.
- **Editing model**: Select-then-act. Keys bind to named commands, not to other key sequences. No key-to-key remapping.
- **Scripting**: Steel (Scheme) for plugins and configuration. Rust handles performance-critical paths; Steel handles behavior and customization.
- **`.scm` files carry a banner only, never prose**: `hume-scripting/src/builtins/bootstrap.scm` and `print_gate_shims.scm` are `include_str!`'d verbatim into a `&str` const and parsed by Steel — their explanatory prose lives in the Rust comment block above that const in `builtins/mod.rs`, never in the `.scm` itself. `runtime/scheme/*.scm` follows the same shape for a different reason: it ships to every user's disk (`scripts/stage.sh` copies `runtime/` wholesale), and its prose lives in that directory's `README.md` (`prelude.scm`'s in `prelude.md`) instead. Both are carve-outs from "record the *why* at the implementing site" — a `.scm` file's nearest implementing site is a Rust doc comment or a sibling README, never itself. Prose that already has a home elsewhere (a builtin's own Rust doc, `docs/LSP-INSTALL.md`'s design rationale) stays there and is not duplicated into the README either.
- **"engine" is overloaded — disambiguate**: Bare "engine" always means the `hume-engine/` crate. The Steel VM is "Steel engine" in prose and `steel` (or `SteelEngine`) as field/type — never a bare `engine` field. Applies to comments and docs alike.

## Day-one architectural invariants
These must be respected from the first line of code — retrofitting is expensive:
- **Selections**: Selections live in a `SelectionSet` (`Vec<Selection>` + `primary: usize` index, kept sorted by start, non-overlapping, non-empty). All edit operations iterate over selections. Selections are always inclusive — `anchor == head` is a 1-char selection covering the character at that index, never a zero-width point.
- **Grapheme clusters**: All motions, selections, and edit operations work on grapheme clusters (`unicode-segmentation`), never raw bytes or `char`. This is the text boundary abstraction — retrofitting is expensive.
  - **Forbidden**: stepping a buffer position by a raw `+ 1`/`- 1` in any motion or selection code. This skips over combining sequences (e.g. `é` = U+0065 + U+0301) or ZWJ emoji instead of advancing a full grapheme cluster.
  - **Required**: `next_grapheme_boundary(text, pos)` and `prev_grapheme_boundary(text, pos)` from `hume-editing/src/grapheme.rs` for all position advances in motion/selection logic.
  - **Allowed**: `line += 1` for line-level iteration, `i += 1` in bracket/delimiter scanning (ASCII only).
  - **Enforced**: the compiler, via `CharOffset` (below) — see that entry's own Enforced line. The one hazard no type can reach is `&str`-level: `s.chars().next_back()`/`s.chars().last()` return `s`'s last *codepoint*, not the base char of its last grapheme cluster (a trailing combining mark); `hume_rope::grapheme::prev_str_boundary` is the fix. This has no automated check — the source-scanning lint that used to catch it was deleted once `CharOffset` closed the rest of the gap it covered — so it relies on ordinary review.
- **Buffer char offsets**: Every buffer position — `Selection::anchor`/`head`, motion and text-object results, `ChangeSetBuilder`'s running cursor — is a `hume_rope::offset::CharOffset` (`hume-rope/src/offset.rs`), never a bare `usize`. A `CharOffset` is minted three ways: `::new` (trusted, no rope check — the value is already known valid, e.g. read back from another `CharOffset`, or the result of an ASCII-only scan), `::checked` (validates against a `&Rope`, `None` past `len_chars()` — Steel builtin args, a restored session position), and `Default` (offset 0 — the type derives it). There is no `::clamped`/`::snapped` mint: a wire position clamps line-then-column (`hume_rope::position_encoding::wire_to_char`), and landing on a grapheme boundary is `hume_rope::grapheme::snap_to_cluster_start`'s job directly — both are a more specific operation than a blind `idx.min(rope.len_chars())` on an already-known `CharOffset` would be. `.index() -> usize` is the escape hatch into ropey, tree-sitter, or any other foreign coordinate system with no domain of its own. A char *count* between two offsets is `CharOffset::chars_since` (debug-asserting on inversion, not a `Sub` impl — a raw subtraction would silently wrap); `CharOffset::shift(delta: isize)` repositions by a signed delta already known to preserve grapheme alignment. `Selection::end_exclusive`/`content_end_exclusive` replace the `end_inclusive(text) + 1` idiom that used to compute an exclusive bound by hand. `ExclusiveRange<CharOffset>`/`InclusiveRange<CharOffset>` (same module) name the two range conventions the codebase mixes — half-open (`ChangeSet`'s position-mapping API, viewport/diagnostic ranges, anything feeding `text.slice()`) vs. both-ends-covered (`Selection`, every text-object/bracket/quote/tag/search finder) — instead of leaving a bare `(usize, usize)` to mean either. Each range type keeps only the operations a real caller uses: both `ExclusiveRange` and `InclusiveRange` are `::new` plus field access plus `contains` (no `is_empty`/`Into<Range<usize>>` — the two production sites that do convert one to a plain `Range<usize>` (`commands/edit.rs`, `hume-ops/src/edit/insert.rs`, both feeding `text.slice()`) build it from the two `CharOffset`s directly rather than through a trait method); `InclusiveRange<CharOffset>::end_exclusive` (`self.end.shift(1)`, not a raw `.index() + 1`) is the inclusive→exclusive crossing every `text.slice()` call against an inclusive result needs.
  - **Enforced**: the compiler — `CharOffset` has a private field and no `Add`/`Sub`/`AddAssign` impls, so `pos + 1`/`head - 1` don't type-check. Two places a buffer position stays plain `usize`: the Steel/LSP host boundary (`hume_scripting::host::Host`, `hume-editor/src/editor/host_impl.rs`) — a documented FFI contract (`docs/LSP.md`) that Steel, having no `CharOffset` of its own, decodes as a raw integer regardless — converting to/from `CharOffset` immediately at that seam; and `hume_engine::types::Grapheme.char_offset` (`hume-engine/src/types.rs`), which needs a `usize::MAX` sentinel for a virtual display line's cells (no buffer position at all) that `CharOffset` has no room to represent — the comparison sites in `hume-engine/src/style/mod.rs` and `hume-engine/src/display_lines.rs` document the trade-off.
- **Line counts and ranges**: Every "how many lines" / "which line is last" / "range of lines" computation goes through `hume-rope`'s four functions (`ropey_line_count`, `last_ropey_line`, `content_line_count`, `last_content_line`) — or a `hume_editing::text::BufferText` method that delegates to one of them — never a raw `len_lines()` call. (Production never walks a whole buffer by line index — the render path walks a viewport window, motions scan outward from the cursor — so there is no whole-buffer *range* function alongside these four; a test needing to walk every line writes the one-line `(0..count.get()).map(Type::new)` inline.) `hume-rope` distinguishes *ropey domain* (the phantom trailing line the buffer invariant's structural `\n` creates, included) from *content domain* (that phantom line excluded) — conflating the two is an off-by-one. The distinction is a compile-time one, not a naming convention: `hume_rope::line::{RopeyLine, ContentLine, RopeyLineCount, ContentLineCount}` (`hume-rope/src/line.rs`) wrap the two domains in distinct types with no `Add`/`Sub` impl, so a raw `line + 1`/`count - 1` on one of the four functions' own result doesn't type-check. `down(n)` (both types) and `up(n)` (`ContentLine` only — a ropey-domain line has no saturating-up caller) are a *named* escape from that ban, not a hole in it — a legitimate re-derivation (`last_content_line(rope).down(1)`) compiles and is the sanctioned way vertical-motion code steps a line, but it also means the deleted line-count lint's literal forbidden textual pattern (a `.down(1)`/`.up(1)` re-derivation of a four-function result) is unenforced today; every current call site operates on locally-derived lines, so this is a documented gap, not a live violation. A bare-`usize` loop bounded by two typed endpoints' own `.index()` (`for line_idx in start_line.index()..end_line.index() { … ContentLine::new(line_idx) … }`, `hume-ops`'s `edit::join`/`edit::sort`/`selection_cmd::matching`) is separately unenforced the same way, since `ContentLine::new` being `pub` admits re-minting the loop variable on every iteration instead of stepping the already-typed endpoint with `.down(1)`; every current call site is correct regardless. `line_break_char(text, line)` is `next_line_start(text, line) - 1`'s replacement for the one pattern the types can't reach (both sides are already-`usize` char offsets) — named for what it is, so the subtraction reads as the mistake it would be. `RopeyLine` is minted two ways: `::new` (trusted, no rope check — the value already known valid) and `::clamped` (clamps against a `&Rope`) — no `::checked`, since every ropey-domain index up to and including the phantom trailing line is valid by definition. `ContentLine` adds `::checked` (validates, `None` past the last real line) and `::from_number` (a 1-based line number — a Steel builtin argument, a `:goto` target). Both types also derive `Default` (line 0), one further mint each beyond the ones named above. A `RopeyLine` narrows to a `ContentLine` via `.to_content(rope)` (`None` on the phantom line) — production code narrows a phantom-admitting value with a *trusted* mint (`ContentLine::new(line.index())`) exactly where a caller already proved the value can't actually be the phantom line, reserving the validating forms for input whose domain isn't yet established. Two documented carve-outs from the domain types themselves: `hume-ops/src/motion/paragraph.rs` scans bare `usize` content-domain line indices internally, and `hume-editor/src/editor/visual_move.rs`'s vertical-motion math scans bare `isize` ones — both with their own in-file rationale.
  - **Enforced**: the compiler — `RopeyLine`/`ContentLine`/`RopeyLineCount`/`ContentLineCount` have private fields and no arithmetic trait impls, so a function typed to take one can't be handed the other, and `line + 1`/`count - 1` don't type-check. `clippy.toml`'s `disallowed-methods` list bans `ropey::Rope::len_lines`/`RopeSlice::len_lines`/`line_to_char`/`char_to_line` workspace-wide (`scripts/test-all.sh`/CI run `cargo clippy --workspace --all-targets -- -D clippy::disallowed_methods`); `hume-rope/src/lines.rs`'s `ropey_line_count` and its sibling line-start/line-count functions are the sanctioned wrappers, the file carrying one `#[allow(clippy::disallowed_methods)]` for all of them. Clippy lints only what compiles for the current target, and CI runs `ubuntu-latest` only — a banned call behind `#[cfg(windows)]` is invisible to this gate where a text scanner would have read it regardless of cfg. No live violation today; if Windows-gated code ever needs one of these four functions' underlying call, review it by hand.
- **Display columns**: Every "how many terminal columns does this text occupy" computation goes through `hume_rope::width` (`tab_advance`, `grapheme_width`, `str_width`) — never a direct `unicode-width` call. Grapheme *indexing* (`hume-rope/src/grapheme.rs`) counts clusters, not cells; LSP wire positions (`hume-rope/src/position_encoding.rs`) count UTF-16 code units or bytes — neither is a display column. `hume_rope::width` itself stays primitive `usize`/`u32` by design, not domain-typed like the "Line/buffer columns" entry below: it's the raw measurement layer (the `CharOffset` refactor's analogue is ropey itself), called with display-line-relative columns (`hume-engine`'s formatter), buffer-line-relative ones (`hume-ops`'s tab/indent math), and run-relative terminal-cell offsets (`hume-grid`'s `Canvas`) alike, so it cannot commit to one origin. Callers narrow with a domain type's `.get()`, the same escape hatch `CharOffset::index()` provides into ropey.
  - **Drawing follows the same model**: text is written to the frame with `Canvas::write_text_run`/`fill_glyph_run`/`write_cell`/`fill_rect_bg`/`fill_row_bg` (`hume_grid::Canvas`, re-exported as `hume_engine::render::Canvas`), never straight through `hume_grid`'s own `Grid::set_glyph`/`fill_span` — those are `pub(crate)` to `hume-grid`, so a call from anywhere else is a compile error, not a lint finding. They are what the canvas is built on — they enforce the head/continuation pairing every wide glyph depends on — but they are one layer too low for drawing code: a bare cell write clips only at the grid's edge, applies no per-pane dim, and substitutes nothing for a cluster the terminal must not be shown as itself. `write_text_run` walks by `grapheme_width`, renders such a cluster — a control character the terminal would act on, an invisible one it would collapse — as its codepoint (`<200b>`, the form Vim and Emacs use, styled `ui.virtual.invisible`) rather than as a blank, since a bidi override that renders like a space is the Trojan Source attack, and takes a `right_edge` so a field sized with `str_width` can't bleed through a pane, lane, or box border. `fill_glyph_run` is its span counterpart for repeating one compile-time-constant glyph (a border line, a scrollbar track) without building a `String` first. `write_cell` is the single-glyph primitive underneath both, `pub` (not `Canvas`-internal) so `hume-engine`'s per-cell compose loops can call it directly — it takes the same `right_edge` bound rather than being exempt from it. A cell records the width its writer measured rather than letting anything downstream re-derive it, so the frame diff and the escape-sequence emitter consume the same number this model produced. Full rationale lives on `Canvas::write_text_run`'s own doc comment (`hume-grid/src/canvas.rs`); every other mention (this one included) is a pointer, not a second copy.
  - **Enforced**: `clippy.toml`'s `disallowed-methods` list bans `unicode_width`'s own methods workspace-wide (`scripts/test-all.sh`/CI run `cargo clippy --workspace --all-targets -- -D clippy::disallowed_methods`); `hume-rope/src/width.rs` itself and a handful of independent-oracle test assertions carry `#[allow(clippy::disallowed_methods)]`. Same `#[cfg(windows)]` blind spot as the line-count entry above — real gated surface exists (`hume-platform/src/{process,path,dirs}.rs`, `hume-lsp/src/uri.rs`); no live violation today.
- **Line/buffer columns**: "Column" means five different things in this codebase, and four of them are domain types in `hume_rope::column` (`hume-rope/src/column.rs`), matching `CharOffset`/`RopeyLine`/`ContentLine`'s own convention: `DisplayLineCol`/`BufferLineCol` (terminal cells, tab-expanded — origin split below), `CharCol` (char index in line), `GraphemeCol` (grapheme-cluster index), `ByteCol` (byte offset in line). A bare `*LineCol` is always display cells; a unit prefix (`Char`/`Grapheme`/`Byte`) names any other unit. LSP wire positions use a bare `character: usize`, matching the protocol's own term and its own code-unit domain — never one of these four. A terminal/pane cell coordinate uses the `x`-family (`screen_x`, `content_x`, `pane_x`) and `hume-grid`'s own `u16`, never a column type. The fifth sense — the full word `Column` in a CamelCase type name (`GutterColumn`, `SignColumn`, `LineNumberColumn`) — names a gutter *widget*, not a coordinate, and has no type here; a lane-bound local variable is named `lane`, never `col`.
  - **A display column also has an origin**: under soft wrap, a continuation display line renumbers its columns from its own left edge, so "display column" means two different things depending on whether it's counted from the display line or from the whole buffer line — the same character has a different number in each. With wrapping off the two coincide (`BufferLineCol::as_display_line_unwrapped` is the one sanctioned crossing, for exactly that case). `DisplayLineCol`/`BufferLineCol` are two concrete types for this, not a single phantom-typed `DisplayCol<Origin>` — the origin is chosen at runtime (`hume-editor`'s vertical motion reads the live wrap mode), so a phantom parameter would only have to be erased right back out. `Selection::sticky_display_col` (`hume-editing/src/selection/single.rs`) is `StickyDisplayCol::DisplayLine { display_col: DisplayLineCol, wrap_width: Option<u16> } | BufferLine { display_col: BufferLineCol }` for the same reason `CharOffset` forbids `+ 1`: a vertical motion reusing a latch tagged with the wrong variant would read a display-line-relative number as a buffer-line-relative one (or vice versa) and land sideways — the enum makes that a compile error at the read site instead of a runtime bug.
  - **Positions, not counts**: unlike `CharOffset`, a display column is a genuine accumulator — formatting advances one grapheme's width at a time — so `DisplayLineCol`/`BufferLineCol` keep a private field but expose named arithmetic (`advance`/`cells_since`/`cells_since_saturating` shared by both; `abs_diff` on `DisplayLineCol` alone, `shift` on `BufferLineCol` alone — each has exactly one origin's worth of real callers) instead of forbidding it outright. `CharCol`/`GraphemeCol` see no such arithmetic anywhere in the codebase and stay as strict as `CharOffset` — mint via `new`/`index()` only. `ByteCol` has one named exception, `advance` (a byte length folded onto a byte column, its two real callers a tree-sitter edit's end position and a bracket match's end byte); every other operation on it stays as strict as `CharOffset`.
  - **Enforced**: the compiler — all five types have a private field and no `Add`/`Sub`/`AddAssign` impls, so `col + 1` doesn't type-check and a function typed to take one can't be handed another. The naming scanner this invariant used to rely on was deleted, and the types cannot close its whole gap: a bare `usize`/`u16` named `col`/`column` in a crate with no column type of its own (`hume-grid`, `hume-platform`, `hume-scripting`, `hume-lsp`) is invisible to the compiler — clean today, unenforced tomorrow. `hume-scripting/src/host.rs`'s `LocationDisplay.grapheme_col_or_wire: usize` is the sanctioned display-value exception from the entry above, and its *name* is the only thing carrying that meaning; no type can. `hume-scripting`'s two other bare `char_col: usize` FFI params (`host.rs`, `builtins/edits.rs`) are the addressing-unit case the same rule permits — a Steel builtin argument, never rendered — and are likewise clean only by convention. Nor can any type police the fifth sense above — a *new* `FooColumn` CamelCase type actually naming a gutter widget rather than a coordinate — which the deleted scanner's allowlist enforced by construction.
  - **Displayed value**: every column HUME *shows* a user (statusline, `:diagnostics`, LSP goto/references) is a 1-based `grapheme_col`/`grapheme-col` — the unit the editing model itself counts in. `char_col`/`char-col` and LSP wire `character` are addressing units only (feeding `goto-location!`, decoration setters, protocol requests) and must never be rendered directly. **One sanctioned exception**: the goto/references drawer's column for a target with no open buffer (`lsp-locations->display-parts`, `hume-editor/src/editor/lsp/introspect.rs`'s `location_display_parts`) renders the location's own wire `character` verbatim rather than reading the file to convert it — the file may never be opened, so counting graphemes in it isn't worth a disk read. The value carrying that union is named for both possible units (`grapheme_col_or_wire`/`grapheme-col-or-wire`), never bare `grapheme_col`, so its own name doesn't overclaim. Nowhere else may this exception be cited.
- **Buffer lines, display lines, and rows**: three words, three meanings, never interchanged. A **buffer line** is a `\n`-delimited line of the rope (`RopeyLine`/`ContentLine`, above). A **display line** is one visual line a buffer line occupies once soft wrap, provider-injected virtual lines, and tilde filler are accounted for — `hume-engine`'s `DisplayLine`/`DisplayLineKind`/`DisplayLineMap`/`DisplayLinePos` (`hume-engine/src/display_lines.rs`, `types.rs`), the single flattened view every render/scroll/cursor/mouse/movement consumer walks instead of estimating "how many lines fill the screen" itself. `DisplayLinePos { line, slot }` addresses one: `line` names the buffer line, `slot` its index within that line's own visual block (`before`-virtuals, then the line's own wrap/content display lines, then `after`-virtuals, in that order) — `ViewportState::top_slot` is this same `slot`, paired with `top_line`. `slot` is display-line-exclusive vocabulary within `hume-engine`'s viewport/scroll machinery; a same-named but unrelated concept (how many panes share a split) lives in `hume-engine/src/pipeline/layout.rs` as `share`/`shares_along`, not `slot`, specifically so the two never collide under one name in the same crate — see "'engine' is overloaded" below for why that collision would matter. One documented carve-out from that same-crate exclusivity: `hume_engine::builtins::sign_column::Sign::slot` is a *user-facing* term (the gutter sign slot a plugin reserves via `register-sign-source!`, `user-manual/docs/plugin-api.md`) predating and unrelated to the display-line sense — same shape as `:sort`'s user-facing "row" carve-out below. A **row** is a terminal or pane cell row (the *y* axis) — `screen_row`/`start_screen_row`, `hume_grid::Grid::row`/`RowRun`/`Canvas::fill_row_bg`, and every widget's own rows (a picker/menu/drawer's `list_rows`/`selected_row`/`styled_rows`), none of which know or care about buffer or display lines. The three coincide only by accident (an unwrapped, undecorated line's one display line happens to land on one terminal row) and the types never assume it.
  - **The `y`-family mirrors the `x`-family**: just as a terminal/pane cell *column* uses the `x`-family (`screen_x`/`content_x`/`pane_x`) rather than a column type (see "Line/buffer columns" above), a terminal/pane cell *row* stays a bare `u16`/`usize` named `row` or `*_row` (`screen_row`, `y` in `hume-grid`) — never a display-line type. A display-line *count* or *address* (`DisplayLineMap::advance`'s `delta`, `DisplayLinePos`) is never spelled `row`.
  - **Two carve-outs, both load-bearing**: tree-sitter's own `Point { row, column }` (`hume-treesitter/src/edits.rs`, `hume_rope::lines::advance_byte_point`) is a foreign coordinate system this codebase decodes, not one it defines — its `row` counts `'\n'`s in a byte range, unrelated to either buffer or display lines, and is never renamed to match. `:sort`'s user-facing vocabulary (the `:sort` error text, `user-manual/docs/command-mode.md`) calls a buffer line a "row" for the end user, predating and unrelated to this distinction — the internal type is `hume_ops::edit::sort::SortEntry`, never "Row".
  - **Enforced**: none — the only invariant on this page with no automated check. The naming distinction is compiler-invisible (all three are ultimately `usize`/`u16`-backed), and the one lint that used to text-scan for it excluded test directories by design even before its deletion, so test names, prose, and cross-references were always outside its reach. Relies on ordinary review; a drifted identifier here compiles clean.

## Rust coding philosophy
This project is both a product and a learning journey. Write the best Rust possible, and teach as you go.
- **Idiomatic first**: Use the type system, iterators, pattern matching, and ownership as intended. Don't fight the borrow checker. Follow current best practices.
- **Performance by design**: Choose the right data structures and algorithms upfront. Avoid allocations in hot paths, use iterators over index loops.
- **No magic**: No macro-heavy abstractions that hide what's happening. Macros only when they genuinely reduce boilerplate.
- **Clean and readable**: Performance and clarity are not at odds in Rust — the compiler optimizes idiomatic patterns well. When in doubt, prefer the version a newcomer can follow.

## Documentation audiences
Every piece of writing in this repo targets one of three audiences. Know which one before you write, and don't mix them.

1. **End users** — people running HUME who want to use it. Lives in `CHANGELOG.md`, `README.md`, `user-manual/docs/*.md`, `runtime/tutor.rst`, `runtime/init.scm.example`, and any `:help`-style content surfaced inside the editor.
   - No internal names. Don't reference Rust types, Steel builtins used only by the implementation, or module paths. ❌ "the next key pressed is passed as `(pending-char)`" — `pending-char` is a code internal; describe the *behaviour* instead.
   - No babysitting. Assume the reader can follow a short instruction. ❌ "These are absent on a fresh setup" — say what to do, not what the reader will or won't see.
   - Describe what the editor does and how to drive it. Nothing about why it's built that way.

2. **Learners / curious developers** — people who want to understand HUME's *concepts*, not its code yet. Lives in `docs/LEARNING.md` and `docs/learning/*.md`.
   - High-level explanations of ideas: the text model, motions vs text objects, the undo tree, etc.
   - No source-file paths, no `editor/src/...` references, no function names. If the explanation needs them to land, it belongs in a source comment instead.
   - Code snippets are fine when they illustrate an *idea*; they should read as pseudocode-with-Rust-syntax, not as a tour of the actual implementation.

3. **Source readers (contributors)** — people with the file open, or one directory away from it. The doc surface for this audience is inline source-code comments, plus a per-directory `README.md` (e.g. `scripts/README.md`, `runtime/scheme/README.md`, each `runtime/plugins/core/*/README.md`) for prose a comment can't carry without either drowning the code it sits in or getting duplicated across every file it'd otherwise need repeating in. Conversely, source-code comments and these READMEs target only this audience — never an end user, never a learner.
   - Add a brief comment when the *why* is non-obvious; never narrate the *what* (well-named identifiers handle that).
   - When choosing between multiple valid approaches, briefly note why this one.
   - Point out important Rust concepts in use (ownership, lifetimes, traits, iterators), especially when the feature might be unfamiliar.
